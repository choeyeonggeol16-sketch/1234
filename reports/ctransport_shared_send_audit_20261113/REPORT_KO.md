# 공유 평문 방송 경로: 원본 바이너리와 ABI9 대조

분석일: 2026-11-13. 비교 기준: `ctransport-core-20261112`의 `fcec7bd7d6a443a09743d53d899d186796934c99`.

**다음 복원 대상으로 타당하다. 원본에는 실제로 “패킷 한 번 작성 → 수신자마다 같은 평문 참조 → 소켓별 암호화 출력” 경로가 있다. ABI9는 마지막 소켓별 처리까지 구현되어 있지만, 여러 수신자가 입력 하나를 공유하도록 연결하는 방송 경로는 없다.** 이미 있는 버퍼 풀·참조 카운트·실행 직렬화·송신 FIFO를 활용해 연결할 작업이다.

이번 변경은 분석 자료만 추가한다. DLL, Java/C++ 운영 소스, 다운로드 ZIP, PSS는 수정하지 않는다. 원본 실행 파일도 실행하지 않았다.

## 1. 근거와 확인 범위

- 대상: 제공받은 x64 `L2Server(10).exe`, image base `0x400000`.
- SHA-256: `9940df15727ec88086cefc036d153fe18c153c9c26a5c90bafe1545de797b588`.
- RTTI의 실제 상속: `CAsyncSendConstBufferExceptSelf → CAsyncSendConstBuffer → CTLMFunc`.
- TypeDescriptor `0xff70b8`, COL `0xeb1ae8`, vtable `0xbcdf68`.
- vtable 설치를 실제 명령어 경계로 확인: `0x57e420`, 상위 함수 `0x57e1d8`.
- 실행 가상 함수: `0x9241f8`. 소멸 함수 `0x9454fc`, 마지막 공통 가상 함수 `0x56daa8`는 `ret 0`.
- PE unwind 정보가 있는 함수는 해당 함수의 전체 범위를 저장했다. 작은 leaf 함수는 도달 가능한 명령어만 최대 512바이트 범위에서 확인했고, JSON/ASM에 구분했다.

이 바이너리는 구형 signature-0 COL에 image-relative 참조를 사용한다. signature-1 형식만 찾으면 클래스를 놓친다. 클래스 이름 검색만으로 동작을 판정하지 않고, COL·상속·vtable 설치·가상 호출·하위 함수까지 연결했다.

이 보고서는 위 x64 파일의 확인 결과다. 함께 제공된 x86 파일의 동일 동작까지 검증했다고 주장하지 않는다. 아래 필드의 설명 이름은 동작을 해석한 것이며, 디버그 심볼에서 원래 멤버 이름을 추출한 것은 아니다.

## 2. 실제 호출 흐름

```text
CThreadLocalWorldMap2<100000,50000,8>::BroadcastToNeighborExceptSelf
  0x57e1d8: 포맷/인자를 받아 공유 평문 버퍼 하나 작성
       ↓
  0x924a9c → 0x924318: 월드 순회 + 필터 + CTLMFunc 가상 실행
       ↓ 수신자별
  CAsyncSendConstBufferExceptSelf 가상 함수 0x9241f8
    유저인지 확인 → 자기 ID 제외 → 해당 소켓 대기량 확인
    공유 평문 AddRef
       ↓
  CExecutionSerializerFast::AddExecutable 0x45c7ac
       ↓ 소켓별 직렬 실행
  CSocket::__async_AsyncSendConstBuffer 0x90e6c4
    공유 평문 → 소켓 전용 출력에 복사/암호화 → 송신 큐/WSASend
    공유 평문 참조 해제
```

상위 함수 이름은 `0x57e245`에서 참조하는 바이너리 내부 UTF-16 함수 서명으로 확인했다. `neighbor_scan.asm.txt`의 `0x92438d`에는 `FOR_ALL_XYZ_INDEX(..., CTLMFilter &, CTLMFunc &)` 서명도 남아 있다.

월드 순회는 `0x9244a7`에서 필터를 호출하고, 통과하면 `0x9244bd`에서 방송 함수의 가상 슬롯 `+8`을 호출한다. 선택된 `CTLMFilterContainer::CanDo` 자체는 true를 반환한다. 별도의 순회 범위/분기까지 포함한 경로이므로 이 메서드만 보고 L1 화면 거리 판정과 같다고 볼 수 없다.

## 3. 제외 대상과 전송 대기량

`functor_slot_0_1.asm.txt`에서 다음 순서를 확인했다.

| 동작 | 원본 근거 |
|---|---|
| 유저 판별 | `0x92420c`: 객체 vtable `+0x168` 호출 |
| 유저 객체 취득 | `0x92421c`: vtable `+0x208` 호출 |
| 자기 자신 제외 | `0x924225`에서 유저 `+0x18`과 방송 객체 `+8` 비교, 같으면 `0x92422b`에서 건너뜀 |
| 소켓 취득 | `0x924233`: 유저 vtable `+0xb28` 호출 |
| 대기량 제한 | `0x924239..0x92423f`: 소켓 `+0x20 >= 방송 객체 +0x18`이면 건너뜀 |
| 공유 입력 유지 | `0x924245`: 입력 버퍼 `+0x4020` 원자 증가 |
| 소켓 직렬 실행 등록 | `0x92427a`: `0x45c7ac` 호출, 콜백은 `0x90e6c4` |

“자기 자신”의 기준은 마우스·IP·소켓 번호가 아니다. **방송을 시작할 때 source 객체 `+0x18`에서 복사한 객체 ID**다(`0x57e261`, `0x57e408..0x57e40c`). source가 없으면 기본값 0이다.

가상 슬롯의 의미도 `User`의 RTTI/vtable `0xd99f18`로 대조했다. `+0x168`은 true 반환, `+0x208`은 this 반환, `+0xb28`은 유저 `+0x35c8`의 소켓 포인터 반환이다. `CObject`의 대응 슬롯은 false/null이다. 실제 메서드 철자까지 확정했다는 뜻은 아니다.

소켓 `+0x20`은 전송 대기 바이트다. `0x90e758`에서 보낼 길이를 더하며, `CUserSocket`의 쓰기 검사 `0x9ef5ca`는 같은 필드를 2 MiB와 비교한다. 오류 문자열에도 `UserSocket pending write > %d KB, Close!`가 있다.

여기에는 두 종류의 제한이 있다.

- **방송별 선택 제한:** 호출자가 넘긴 값 이상이면 그 방송을 해당 수신자에게 보내지 않는다. 이 분기 자체가 소켓을 닫지는 않는다. 새 패킷 길이를 더하기 전 대기량 검사다.
- **소켓 쓰기의 최종 제한:** 실제 실행에서 패킷 길이를 더한 뒤 2 MiB 검사를 한다. 방송 선택 제한과 별개다.

호출부에서 실제 값도 확인했다.

| 호출부 | 전달한 방송 한도 | 호출 위치 |
|---|---:|---|
| `CCreature::ChangeTarget` | `0x5000` = 20 KiB | `0x58091e` |
| `BroadcastValidateLocation` | 20 KiB | `0x580bf7` |
| `CCreature::ValidateLocation` | 20 KiB | `0x58114d` |
| `CGetOffVehicleIOCPMessage::OnReceive` | `0x80000` = 512 KiB | `0x7074be` |
| `CGetOffShuttleIOCPMessage::OnReceive` | 512 KiB | `0x707886` |
| `User::SendPrivateStoreMessage` | 512 KiB | `0x967dc7` 등 |

기본 클래스 `CAsyncSendConstBuffer`의 함수 `0x924164`도 대조했다. 자기 ID에 해당하면 대기량 선택 검사를 우회해 전송하고, 다른 대상만 한도를 검사한다. `ExceptSelf`는 자기 ID를 전송 대상에서 제외한다. 두 클래스의 차이가 실제 분기로 존재한다.

## 4. 공유 버퍼 수명

1. `0x41f694`가 버퍼 하나를 할당하고 포맷을 한 번 작성한다. payload는 `+0x10`부터이며 2바이트 길이 뒤에 본문을 쓴다. 이 원본 경로의 최대 wire 길이는 16 KiB다.
2. allocator `0x41e6e4`는 `+0x4020` 참조를 1로 만들고, `+0x4034`에 반환할 풀 소유자를 기록한다.
3. 전송 대상으로 선정된 수신자마다 참조를 하나 추가하고 같은 버퍼 포인터를 넘긴다.
4. 소켓 콜백은 원본 입력을 변경하지 않고, 해당 소켓의 출력 버퍼에 본문을 암호화하며 복사한다(`0x90e812`, `0x90ea38`, `0x90eaa7`). 암호화 비활성 분기는 일반 복사다.
5. 콜백이 입력을 소비한 뒤 참조를 내린다(`0x90eb08`). 입력이 비었거나 이미 닫힌 소켓도 참조를 내린다(`0x90eb4c`). 쓰기 검사 실패도 반환 경로가 있다(`0x90e769`).
6. 월드 순회를 마치면 생성자의 참조 하나를 내린다(`0x57e43b`). 마지막 참조가 사라지면 길이/next를 초기화하고 기록된 소유자 풀에 돌려준다.

참조 수의 의미는 **생성자 1개 + 아직 소비/회수되지 않은 수신자 참조 수**다. 즉시 실행된 수신자의 참조는 순회 도중 이미 사라질 수 있다.

**공유 입력의 수명은 네트워크 송신 완료까지가 아니다.** 각 수신자의 암호화 출력에 복사한 뒤 공유 입력 참조를 반환한다. 이후의 비동기 송신/부분 완료는 소켓 출력 버퍼의 별도 수명이다. 한 사람의 암호문을 다른 사람에게 공유하는 구조도 아니다.

또한 `AddExecutable`은 항상 IOCP에 작업을 게시하는 함수가 아니다. 같은 실행 소유자면 `0x45c82c`에서 즉시 호출하고, 그 외에는 직렬 큐와 단일 실행 소유자가 처리한다(`0x45c994`).

원본 오류 처리에는 그대로 가져오면 안 되는 부분도 있다. 직렬 큐 초과 시 `AddExecutable`은 -1을 반환하지만, 위 방송 가상 함수에는 반환값을 검사해 선행 AddRef를 되돌리는 분기가 보이지 않는다. 중간의 `0x6704e0`는 호출 스택 로깅이며 해당 인자로는 복귀한다. 이 경로를 복원할 때는 **등록 거절 시 참조·예약량을 명시적으로 되돌려야 한다.** 전체 서버의 다른 회수 경로 존재 여부까지 단정하지는 않는다.

## 5. 현재 L1과의 차이

| 항목 | 원본 확인 결과 | 현재 ABI9 |
|---|---|---|
| 방송 평문 작성 | 포맷 한 번, 버퍼 하나 | 액션/이펙트는 수신자별 직접 프레임 작성 |
| 네이티브 입력 | 같은 입력 포인터를 여러 소켓이 참조 | `NativeSendRequest`마다 `std::vector`에 별도 복사 |
| 소켓별 암호화 출력 | 별도 출력에 복사하며 암호화 | 구현되어 있음 |
| 소켓별 FIFO/직렬 실행 | `AddExecutable` + 출력 큐 | 구현되어 있음 |
| 버퍼 풀/참조 카운트 | 고정 풀, 원자 참조, 소유자 반환 | 구현되어 있음. 방송 입력으로 연결되지 않음 |
| 자기 제외 | source 객체 ID | L1 화면 조회에서 이미 같은 ID 제외 |
| 방송 종류별 대기량 선택 | 20/512 KiB 등 호출자 지정 | 조사한 방송 경로에 이에 대응하는 선택 기능 없음. 최종 큐 제한은 별도로 존재 |

현재 코드의 직접 근거:

- `native/CTransport.cpp:416`: `NativeSendRequest`가 요청마다 vector를 만들고 입력을 복사한다.
- `native/CTransport.cpp:462`: const 경로는 그 vector를 소켓별 출력에 옮겨 암호화한다. gather는 한 소켓에 여러 조각을 보내는 기능이며, 여러 소켓의 입력 공유와 다르다.
- `native/cio_core.hpp:41`, `:135`: 원본 레이아웃의 `CIOBufferEx`, retain/recycle은 이미 있다. 재구현할 필요가 없다.
- `src/.../core/sc/packet/SC_DoActionGFX.java:56`: 수신자마다 `sendAction`을 호출한다. wire 8바이트다.
- `src/.../core/sc/packet/SC_SkillSound.java:18`: 수신자마다 직접 프레임을 만든다. wire 15바이트다.
- `src/.../model/L1World.java:363`: 재사용 가능한 화면 수신자 목록을 빌린다.
- `src/.../model/LocalWorldMap.java:445`: 같은 객체 ID를 제외하고 화면/거리 판정을 적용한다.
- `src/.../core/CUserSocket.java:3423`: Java FIFO에서 다음 송신과 gather를 선택한다.

## 6. L1에 구현할 구체 범위

**기존 큐 앞단에 공유 입력 참조를 연결하는 것이 다음 작업이다.** 소켓·풀·타이머를 다시 만드는 작업은 필요하지 않다.

1. 이미 있는 `CIOBufferEx` 풀로 평문을 한 번 작성하고 발행 뒤 변경하지 않도록 한다. 수신자마다 참조를 유지하고, 실패·취소·종료마다 정확히 하나씩 반환한다.
2. 원본 이름이 확인된 `CAsyncSendConstBuffer` / `CAsyncSendConstBufferExceptSelf`에 해당하는 방송 동작을 연결한다. L1의 월드/화면 조회와 이펙트 표시 설정은 유지한다.
3. 각 수신자의 **기존 `CUserSocket` FIFO에** 공유 참조를 넣는다. Java에 먼저 예약된 패킷을 두고 DLL로 곧바로 방송하면 앞 패킷을 추월할 수 있으므로 이 우회는 사용하지 않는다. 공개 전 예약된 FIFO ticket도 지켜야 한다.
4. 그 참조가 순서상 실행될 때 `NativeSendRequest`의 수신자별 입력 vector 복사를 생략하고 공유 입력을 읽게 한다. 소켓별 출력·L1 암호키 갱신·완료 콜백·기존 byte/frame 제한은 유지한다.
5. FFM 연결에 필요한 새 함수는 원본에서 확인한 C++ 함수 이름과 구분해 `L1Interop_*` 보조 함수로 명시한다. Java/네이티브 큐가 소유하는 참조의 경계를 확정하고, 네이티브 객체의 파괴 후까지 Java가 포인터를 갖지 않게 한다.

처음 연결하기 좋은 대상은 내용이 수신자에 따라 변하지 않는 액션/이펙트 방송이다. 다만 `broadcastM`의 `LinMeff` 필터, 자기 전송을 별도로 하는 `sendAndBroadcast`, 화면/맵 범위는 그대로 보존해야 한다.

일반 `ServerPacket` 전체를 한 번에 이 경로로 바꾸면 안 된다. `WritablePacket.writeData(client, buffer)`와 `ServerPacket.writeImpl(client, buffer)`는 client를 인자로 받으며 수신자별 내용 변경이 가능하다. 클래스 하나가 여러 사람에게 전송된다는 사실만으로 바이트까지 같다고 보장되지 않는다.

원본의 방송 대기량 제한도 L1 전체에 일괄 적용하면 안 된다. 위치/시각 효과처럼 생략 가능한 데이터와, 인벤토리/거래처럼 순서·전달 의미가 중요한 데이터를 구분해야 한다. 비교한 원본 값은 정책의 근거이지 L1에 그대로 복사할 고정값이 아니다.

L2의 이 함수는 16 KiB 입력 하나를 쓰지만, 현재 L1 const 경로는 여러 16 KiB 블록에 걸친 프레임을 지원한다. 큰 입력은 기존 경로로 넘기거나 별도 공유 표현을 설계해야 하며, 16 KiB로 잘라 L1 지원 범위를 줄여서는 안 된다.

## 7. 기대 효과와 검증 조건

N명에게 L바이트를 보낼 때 목표는 **N번의 평문 작성/입력 복사 → 1번 작성 + N개의 작은 수신자 참조**다. 소켓별 암호화·출력 저장·실제 네트워크 송신량은 여전히 필요하다.

현재 액션/이펙트는 8/15바이트로 작고 이미 직접 작성하는 경로다. 풀 사용량·참조 연산·FFM 비용을 고려하면 더 빨라진다고 확정할 수 없다. 큰 동일 패킷과 많은 수신자에서 이득이 있는지는 별도 측정 대상이다. 이번 분석으로 속도·동접 수치를 만들지 않았다.

구현 후 검증해야 할 실제 실패 조건:

- 서로 다른 키를 가진 여러 수신자: 기존 L1 코덱으로 각각 복호화 시 같은 평문, 공유 입력 해시 불변.
- 먼저 예약된 일반 패킷, 공유 방송, 다음 일반 패킷의 순서와 프레임별 키 갱신 유지.
- 한 수신자의 큐 거절·도중 종료·FFM 호출 실패가 다른 수신자의 출력에 영향 없음.
- 모든 수신자 제외/거절, 일부 즉시 실행, 일부 지연 실행, 직렬 큐 포화 시 참조·예약량 잔류 없음.
- 작은 프레임, 16 KiB 경계, 기존 큰 프레임 지원, partial send, 비동기 완료/오류 시 이중 반환 없음.
- 기존 자기 제외·같은 맵·화면·이펙트 설정 결과 동일. PSS 기존 검사 통과.

## 8. 재현 자료

`trace_shared_send.py`는 제공 바이너리 SHA를 확인하고 RTTI/참조를 다시 찾는다. 근거가 되는 **28개 명령어의 주소·종류·피연산자를 assertion**으로 검사하고, **32개 이름별 함수/leaf ASM 덤프(공통 주소 중복 포함)**와 메타데이터를 생성한다. `trace-evidence.json`의 일반 공통 함수는 무관한 caller가 많아 최대 24개를 저장하고 전체 수/생략 여부를 기록한다.

필요 패키지: `pefile`, `capstone`. Python 실행 예:

```bash
python trace_shared_send.py --binary '/path/to/L2Server(10).exe' --out /tmp/shared-send-evidence
```

현재 소스까지 지문을 남기려면 `--source-root /path/to/aden`을 추가한다. `production-source-hashes.json`은 분석한 src/native 1,720개 파일의 해시를 기록했다. 소스 인덱스 SHA-256은 `b2c0ddcad6d924bb038d5999e7794f98df8c10fe63c1ecf230f4fe15229fec67`이다.

결론의 범위는 **이 방송 경로의 정적 동작과 ABI9의 구체적인 차이 확인**이다. 실행하지 않은 원본의 안정성·성능, 서버 전체 복원율, 원래 소스와의 완전 일치까지 입증한 것은 아니다.

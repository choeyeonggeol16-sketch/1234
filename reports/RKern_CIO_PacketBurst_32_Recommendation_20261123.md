# RKern CIO 패킷 처리 버스트 32개 권장 보고서

- 작성일: 2026-11-23
- 검토 대상: Java 21 RKern, `CIOThreadCallback.CIOThread.MAX_PACKET_BURST`
- 기준 GitHub 브랜치: `rkern/nc-intrusive-inventory-20261122`
- 결정: **32개를 운영 A/B 검증의 우선 후보로 선정**
- 소스 적용 상태: **미적용** (보고서만 추가, 실제 값은 64)
- 실험 범위: Java 21 독립 TCP 재현 테스트. 실제 RKern 통합 서버 부하 테스트와 구분함.

## 1. 핵심 결론

CIO 샤드의 패킷 버스트는 SEND 패킷 병합 개수가 아니다. 하나의 CIO 샤드가 `packetIngress`에서 꺼낸 `PacketTask.run()`을 **최대 몇 개 연속 실행한 뒤 Selector I/O를 처리할지** 결정하는 공정성 예산이다.

기존 64개와 후보 32개를 비교하면, **32개는 1,024연결 경량 패킷 처리량과 256연결 전투형 응답 p99가 더 좋았고**, 64개는 1,024연결 전투형 p99가 더 좋았다. 31과 32의 우열은 일관되게 확정되지 않아 특별한 의미가 없는 31보다 **32를 실무적인 기준 후보**로 택했다.

**권장 행동: 32/64를 실제 RKern에서 같은 부하로 재검증한 후에 기본값 변경 여부를 판단한다.** 독립 테스트 결과만으로 64를 자동 교체하거나 32를 확정된 전역 최적값으로 선언하지 않는다.

## 2. 실제 소스 경로 및 실행 원리

대상 파일:

`rkern/src/l1j/server/server/model/network/thread/CIOThreadCallback.java`

현재 소스에는 다음 정의가 있다.

```java
static final int PACKET_INGRESS_CAPACITY = 8192;
static final int MAX_PACKET_BURST = 64;
```

CIO owner 루프의 핵심 구조는 다음과 같다.

```java
int packetDrained = 0;
PacketTask packet;
while (packetDrained < MAX_PACKET_BURST
        && running && (packet = packetIngress.poll()) != null) {
    try {
        packet.run();
    } catch (Throwable packetFailure) {
        LOGGER.log(Level.SEVERE, "[CIO-PACKET] shard handler failed idx=" + idx,
                packetFailure);
    }
    packetDrained++;
}
// 이후 selectorDriver.advance()로 I/O 처리 기회를 제공
```

실제 루프에는 50ms CIO 타이밍 휠 tick, `selectorDriver.advance()`, backlog 분기, `awaitWork()`가 있다. 타이밍 휠은 각 루프 앞부분에서 만기 여부를 확인한다. 버스트를 줄이면 루프 재진입이 빈번해져 **I/O 확인과 타이머 tick 기회**가 증가할 수 있다. 동시에 잦은 Selector 확인, 큐 폴링 및 스케줄 순환 비용이 증가할 수 있다. CPU 연산 능력이 직접 증가하는 최적화는 아니다.

## 3. 테스트 구성과 검증 범위

이전 대화에서 수행한 Java 21 독립 TCP 테스트 집계 기준:

- 버스트 후보: **4, 6, 8~32 전수, 48, 64, 96, 128** (총 31가지)
- 부하 A: 1,024연결, 게임/전투 연산 혼합, 테스트 회차당 **총 50,000패킷**
- 부하 B: 1,024연결, 가벼운 패킷, 테스트 회차당 **총 50,000패킷**
- 부하 C: 256연결, 게임/전투 연산 혼합, 테스트 회차당 **총 50,000패킷**
- 31가지 구성의 초기 교차 측정, 상위 후보 재측정, 최종 16·31·32·64개 후보 추가 반복을 수행함.
- 이전 보고 집계: **363회, 총 18,150,000패킷**. 각 회차의 송수신 패킷 수와 데이터 무결성을 검증했다고 기록됨.
- 아래 최종 후보 수치는 각 부하 조건에서 **10회 측정한 중앙값**임.
- 참고: 50,000패킷은 **회차당 총량**이며, 초당 50,000패킷을 지속해서 보냈다는 의미가 아니다.
- 본 보고서 작성 시 새 통합 서버 벤치마크를 실행한 것은 아니며, 앞서 생성한 독립 테스트 결과의 집계치를 문서화한다. 전체 원시 데이터는 이전 테스트 ZIP에 포함됨.

## 4. 16 / 31 / 32 / 64 비교

### 4.1 지연과 경량 처리량

| CIO 버스트 | 1,024연결 전투형 응답 p99 | 1,024연결 경량 처리량 | 256연결 전투형 응답 p99 |
|---:|---:|---:|---:|
| 16 | 63.07 ms | 151,860 packets/s | 17.39 ms |
| 31 | 62.74 ms | 152,741 packets/s | 17.23 ms |
| **32** | **64.49 ms** | **155,164 packets/s** | **16.85 ms** |
| 64 (현재) | **61.59 ms** | 144,041 packets/s | 17.42 ms |

32개 대 64개:

- 1,024연결 **경량 처리량**: 155,164 vs 144,041 packets/s, 약 **+7.7%**
- 256연결 **전투형 응답 p99**: 16.85 vs 17.42ms, 약 **-3.3%**
- 1,024연결 **전투형 응답 p99**: 64.49 vs 61.59ms, 약 **+4.7% 악화**

따라서 32개가 항상 승리하는 결과는 아니다. 특히 고접속 전투형의 최악 지연에 민감하다면 기존 64개를 유지할 근거가 있다.

### 4.2 31개를 최적값으로 단정하지 않는 이유

| 지표 | 31개 | 32개 |
|---|---:|---:|
| 1,024연결 전투형 p99 | 62.74ms | 64.49ms |
| 1,024연결 경량 처리량 | 152,741/s | 155,164/s |
| 256연결 전투형 p99 | 17.23ms | 16.85ms |

31과 32는 서로 다른 항목에서 앞섰다. **31이라는 정수 자체에 특별한 알고리즘 최적화나 비트 연산 이점이 있는 것은 아니다.** 회차 변동과 측정 편차를 고려해 32를 우선 실험할 단순한 기준값으로 선정한다.

### 4.3 타이머 지연 관련 관찰

이전 31/64 비교에서 관찰한 타이머 최대 지연의 중앙값:

- 1,024연결 전투형: 31개 **2.05ms** / 64개 **3.46ms**
- 256연결 전투형: 31개 **2.03ms** / 64개 **3.54ms**

위 수치는 **31개와 64개**의 비교다. **32개의 타이머 지연 수치로 대체해 인용하지 않는다.** 32개는 실제 통합 A/B에서 별도로 측정해야 한다.

## 5. 운영 적용 전 필수 비교

실제 RKern의 `MAX_PACKET_BURST` 값만 **32 vs 기존 64**로 변경하여, 그 외 CIO/Selector/SEND/암호화/Timing Wheel 구성은 동일하게 유지한다. A/B 모두 충분한 워밍업과 같은 데이터·부하·JVM·하드웨어 조건에서 실행한다.

필수 시나리오:

1. 16/256/1,024연결, 소형 패킷 고처리량 및 4KiB 패킷.
2. 전투형 혼합 연산(짧은 핸들러 + 간헐적 긴 핸들러), AOI 송신 응답.
3. 샤드 큐가 포화되는 상황과 만성적으로 backlog가 쌓이는 상황.
4. 실제 서버에서 가능한 최대 동시접속에 가까운 부하. 5,000명 목표는 별도 장시간 검증.
5. Windows NIO.2/IOCP와 Linux Selector 실행 정책이 서로 다른 경우 각각 확인.

필수 계측:

- 초당 실제 수신/처리 패킷, 완료 처리량, CPU/패킷.
- 네트워크 왕복 p50/p95/p99/p99.9.
- `packetIngress` 대기 p95/p99, 큐 최대 점유, admission 실패.
- CIO 샤드별 패킷 처리 소요시간·루프 반복 횟수·Selector 점유.
- 50ms Timing Wheel 만기 지연과 최대 연속 handler 점유시간.
- SEND 큐 압력, partial WRITE, 유실·중복·순서 뒤바뀜, 연결 종료 및 재접속 경합.
- 실제 스킬/공격/이동 게임 로직의 동작 등가성.

### 채택 기준

- 32개가 **64개보다 지연을 안정적으로 줄이거나** 동등한 지연에서 **실측 처리량/CPU를 개선**해야 한다.
- 1,024연결 전투형 p99가 재현성 있게 악화되거나, 큐 적체/타이머 지연·오류가 늘면 **64개 유지**.
- 근소한 차이는 변동폭/신뢰구간과 함께 해석하며, 특정 회차의 최고값만으로 선택하지 않는다.
- **개별 패킷에 대한 시간 예산이 없는** 현 구조에서 패킷 수 제한만으로 긴 핸들러의 독점을 완전히 차단할 수는 없다.

## 6. 적용 지침 및 수정 범위

이 보고서는 **권장 실험 설계**이지 production 변경 패치가 아니다. 추후 채택 시 변경 대상은 원칙적으로 아래 정수 한 곳이다.

```java
// 기존
static final int MAX_PACKET_BURST = 64;

// A/B 후보
static final int MAX_PACKET_BURST = 32;
```

기존 CIO 소유 샤드, Timing Wheel, Selector, 패킷 FIFO, SEND 병합, 암호화, 버퍼 풀, 게임 로직을 변경하지 않는다. 새 worker/queue/thread도 추가하지 않는다.

## 최종 결론

**32는 합리적인 1순위 A/B 후보지만, 64보다 언제나 빠른 확정 최적값은 아니다.** 1,024연결 경량 처리량과 256연결 전투형 지연에서 개선 신호가 있고, 1,024연결 전투형 지연에서는 64가 더 우수했다. 따라서 **실제 RKern 통합 A/B에서 32 vs 64 재검증 후 기본값 결정**을 권장한다.

# MJBin 2019 자동 마법인형 소환 역분석 — 이벤트·상태·아이템 사용·패킷 연동

> 분석 일자: 2026-11-13 · 사용자 제공 MJ 프리서버 \`mjlin.bin\` 및 \`mjlin_loaded_code_00400000_0180D000.bin\`. PE32 x86 이미지 베이스 \`0x00400000\`. 주소는 원본 메모리 이미지 **VA**. **구버전 클라이언트에서 실행 검증한 결과가 아니다.**

## 0. 결론

**자동 인형 소환은 전용 소환 패킷 발송부터 시작하는 구조가 아니라, 클라이언트에 이미 있는 인벤토리 아이템 사용 함수 \`0x00B20E60\`을 재사용한다.** UI 옵션은 활성 상태만 변경하고, 게임 내부 이벤트에서 소환 상태를 확인한 뒤 기억 중인 아이템을 조회해 필요한 경우 사용을 요청한다.

- **코드로 확인**: 옵션 상태 토글, 소환 관련 이벤트 ID 0x13·0x95 수신, 소환 상태 분기, 아이템 식별자 저장/해제, 해당 아이템 조회, 타입값 0x49 비교, 기존 아이템 사용 함수 호출, 내부 이벤트 데이터 생성·전달.
- **미확정**: \`0x96\`이 실제 네트워크 opcode인지 여부(현 단계에서는 내부 명령/이벤트 식별자 취급), \`0x00E717A0\` 뒤의 패킷 직렬화·송신 함수, 서버 수신 opcode, \`0x13/0x95\` 내부 이벤트의 정확한 사용자 의미, \`0x49\` 아이템 타입 코드의 명칭.

따라서 L1J 서버가 처리하는 소환 요청은 **기존 아이템 사용 패킷 경로와 연결될 가능성이 높지만**, 원본 TCP opcode 추적을 완료하기 전까지 전용 패킷이 없다고 단정하지 않는다.

## 3. 옵션 ON/OFF 실행 경로

UI \`Action_AutoSummonMagicDoll\` 콜백인 **\`0x00C02CA0\`**은 전역 \`0x015B4E3C\`에서 소환 관리 객체를 얻는다. 없으면 \`0x00A7F190\`을 호출해 확보한다.

- UI 액션과 연동할 첫 진입에서는 \`0x008476D0\`을 이용해 객체 \`+0x14\` 상태 주소를 넘긴다.
- 이후에는 \`0x00847790\`에서 읽은 bool 값을 \`sete\`로 반전하고 \`0x00847650\`으로 기록한다.

원본 x86 증거:

~~~asm
; 0x00C02CF3부터
0x00C02CF3 mov ecx, edi
0x00C02CF5 call 0x00847790
0x00C02CFA test al,al
0x00C02CFE sete al
0x00C02D01 movzx eax,al
0x00C02D04 push eax
0x00C02D05 call 0x00847650

; 상태 저장 0x00847650
0x00847653 mov al,byte ptr [ebp+0x8]
0x00847656 mov byte ptr [ecx+0x14],al
0x00847659 pop ebp
0x0084765A ret 0x4
~~~

**옵션 ON 자체에서 곧바로 전용 인형 소환 패킷을 전송한다고 보이지 않는다.** 실제 조건부 사용 시도는 아래 별도 경로가 담당한다.

## 4. 이벤트 수신 — ID 0x13, 0x95

\`0x008476E0\`은 전달된 이벤트의 구분값을 얻어 다음처럼 비교한다.

~~~asm
0x008476ED mov ecx,edi
0x008476EF call 0x00E6F7F0
0x008476F4 cmp eax,0x13
0x008476F7 je 0x0084771C
0x008476F9 cmp eax,0x95
0x008476FE jne 0x0084775A
~~~

- **0x95** 경로: 이벤트의 \`+0x8\` 필드가 0이고 \`[esi+0x18]\`이 0이 아닐 때 \`0x00847660\` 호출.
- **0x13** 경로: 글로벌 인벤토리/게임 객체 조회 후 연관된 객체에서 소환 관련 정보를 획득, 객체 \`+0x14\`에 기록하고 \`0x00847660\` 호출.
- 이 숫자들은 **내부 이벤트 ID**이다. 인게임 클라이언트의 송수신 패킷 opcode가 아님.

실제 분기 중 일부:

~~~asm
0x00847700 cmp dword ptr [edi+0x8],0x0
0x00847706 cmp byte ptr [esi+0x18],0x0
0x0084770F call 0x00847660
0x0084773F call 0x00B1DF50
0x0084774A call 0x00CBB130
0x00847755 call 0x00847660
~~~

## 5. 상태 확인 후 사용 시도 — 0x00847660

\`0x00847660\`은 소환 관리자 객체를 \`ECX\`로 받는다. 실제 플래그:

| 객체 필드 | 기계어 접근 | 해석 |
|---|---|---|
| \`+0x14\` | \`mov bl,[esi+0x14]\` | 사용자 자동소환 활성화 |
| \`+0x18\` | \`push [esi+0x18]\` | 기억된 인형 아이템 식별자 유력 |
| \`+0x20\` | \`mov [esi+0x20],eax\` | 마지막 시도/아이템 연계 결과 값 |
| \`0x008477A0\` 반환 AL | \`mov bh,al\` | 현재 소환 관련 상태 판정 |

실제 분기:

~~~asm
0x0084766A mov bl,byte ptr [esi+0x14]
0x00847670 call 0x008477A0
0x0084769D test bl,bl
0x0084769F je 0x008476B2
0x008476A1 test bh,bh
0x008476A3 jne 0x008476B2
0x008476A5 push dword ptr [esi+0x18]
0x008476A8 mov ecx,esi
0x008476AA call 0x00847B50
0x008476AF mov dword ptr [esi+0x20],eax
~~~

즉 **옵션 활성화 + \`0x008477A0\` 상태 불충족** 시 저장된 아이템을 사용해보는 경로가 존재한다. 이미 소환되어 있을 때 추가 소환을 회피한다는 해석은 강하나, \`0x008477A0\`이 정확히 어떤 상태 2종을 검사하는지는 아래처럼 내부 코드 의미가 아직 확인되지 않았다.

\`0x008477A0\`이 읽는 두 식별자:

~~~asm
0x008477FB push 0x52
0x008477FF call 0x00F1C9F0
...
0x00847851 push 0x5C
0x00847855 call 0x00F1C9F0
~~~

이들은 **상태값 검사용 코드**이며, 소환 패킷 번호라고 단정하면 안 된다. 사용 시도 뒤 \`0x00847910\`을 호출하는 추가 상태/UI 갱신 분기도 존재한다.

## 6. 수동 아이템 사용 시 기억/해제 — 0x00847AD0

\`0x00847AD0\`은 인자 아이템 ID(유력)를 \`[esi+0x18]\`과 비교한다.

- 같은 ID이고 \`0x008477A0\` 상태 검사에서 AL≠0이면, ID/연계 필드를 해제:
  - \`[esi+0x18] = -1\`
  - \`[esi+0x1C] = 0\`
  - \`[esi+0x20] = -1\`
- 그 외에는 새로운 ID를 \`[esi+0x18]\`에 기록하고 \`[esi+0x1C] = 1\`. 인벤토리 조회 결과에 따라 \`[esi+0x20]\`을 갱신한다.

~~~asm
0x00847ADD cmp dword ptr [esi+0x18],ebx
0x00847AE2 call 0x008477A0
0x00847AEB mov dword ptr [esi+0x18],0xffffffff
0x00847AF2 mov byte ptr [esi+0x1C],0x0
0x00847AF6 mov dword ptr [esi+0x20],0xffffffff
...
0x00847B06 mov dword ptr [esi+0x18],ebx
0x00847B09 mov byte ptr [esi+0x1C],0x1
0x00847B2E call 0x00B1DF50
~~~

\`0x00B20E60\`의 일반 아이템 사용 경로는 전역 소환 관리 객체 획득 함수 **\`0x00B1EB50\`**과 연결되어 있으며, 같은 아이템 정보를 소환 관리자에 기록하는 경로가 있다는 것이 이전 추적 결과다. 정확히 어떤 아이템 사용 분기에서 \`0x00847AD0\`으로 진입하는지와 모든 조건은 추가 확인이 필요하다.

**구버전 이식 관점**: 자동소환 대상은 인벤토리의 첫 번째 인형으로 무조건 고정되는 게 아니라, 실제 사용한 아이템 식별자를 **기억·갱신**하는 패턴이다.

## 7. 아이템 검사 후 기존 아이템 사용으로 진입 — 0x00847B50

\`0x00847B50\`의 실제 코드에서:

1. 글로벌 아이템 관리자 \`[0x015B3A20]\`을 가져옴(없으면 \`0x005EA180\`).
2. \`0x00B19350\`, \`0x00B1DF50\`로 기억한 ID의 아이템을 검색.
3. 조회 실패 시 즉시 반환.
4. \`0x00CBB150\`의 결과 \`AL\`을 **0x49와 비교**.
5. 일치할 경우 기존 아이템 사용 \`0x00B20E60\`으로 진입.
6. 사용 연계값을 추출해 반환하거나 실패 표시 값(초기값 -1)을 유지.

핵심 원본 기계어:

~~~asm
0x00847B82 push dword ptr [ebx+0x18]
0x00847B8D push eax
0x00847B90 call 0x00B1DF50
0x00847B97 test esi,esi
0x00847B99 je 0x00847BE4
0x00847B9D call 0x00CBB150
0x00847BA2 cmp al,0x49
0x00847BA4 jne 0x00847BE4
0x00847BBB push esi
0x00847BBC call 0x00B20E60
0x00847BC3 call 0x00B29550
0x00847BE4 mov eax,edi
~~~

**0x49가 아이템의 어떤 공식 카테고리 이름을 뜻하는지는 이번 정적 분석에서 확정하지 않았다.** 그러나 타입 일치가 사용 시도의 필수 게이트라는 것은 확정이다.

## 8. 아이템 사용 후 내부 전달 및 패킷 여부

기존 아이템 사용 함수 \`0x00B20E60\`에서는 입력 아이템의 상태/타입 및 기타 게임 조건을 검사하는 여러 분기가 존재한다. 그중 일부 경로에는 다음 명령이 있다.

~~~asm
0x00B2135F push 0x96
0x00B21367 call 0x00AC3DF0
...
0x00B213DA call 0x00E717A0
~~~

- **0x96**: \`0x00AC3DF0\`에 전달되는 정수. **TCP opcode라고 확정하지 않음**.
- **0x00E717A0**: 생성된 내부 작업/이벤트를 전송 계층 쪽으로 넘기는 함수로 관찰됨. 정확한 최종 소비자 및 wire serialization은 미추적.
- 따라서 **'새 인형 전용 패킷이 있다'도 '인형 소환은 무조건 기존 아이템 사용 패킷만 쓴다'도 최종 확정 사항이 아니다.**
- 현재까지 직접 확인된 결정적인 사실은 **자동소환이 기존 아이템 사용 함수를 호출한다는 것**이다.

실제 클라이언트↔서버 네트워크 패킷의 정체를 확정하려면 \`0x00AC3DF0\` 생성·\`0x00E717A0\` 최종 전달 소비자→직렬화→소켓 SEND 경로를 추적해야 한다.

## 9. 구버전 DLL / L1J 이식 계획

**목표**: 클라이언트가 자동소환 여부를 판단하되, 서버는 기존 검증된 아이템 사용·소환 처리 경로를 계속 사용.

~~~text
[클라이언트 UI]
  └─ AutoSummonMagicDoll ON
        └─ (내부 게임 이벤트 0x13 / 0x95)
             └─ 소환 상태 확인
                  ├─ 이미 소환/상태 충족 → 추가 요청 없음
                  └─ 미소환 / 조건 통과
                        └─ 기억한 아이템 ID로 인벤토리 조회
                             ├─ 없음 또는 타입 불일치 → 중지
                             └─ 조건 충족 → 기존 아이템 사용 호출
                                  └─ 내부 이벤트 생성
                                       └─ 패킷 송신 경로 [추가 검증]
                                            └─ 서버 기존 아이템 사용/소환
~~~

권장 경계:

1. **클라이언트 x86 DLL**: 설정 bool, 마지막 인형 아이템 ID, 이벤트 트리거, 소환 상태, 중복 사용 차단.
2. **클라이언트 기존 인벤토리/사용 경로**: 아이템 조회·사용 명령. 원본 VA를 다른 버전에 그대로 적용하지 않는다.
3. **서버 L1J**: 아이템 사용 패킷 수신 뒤 소환 조건, 소유/아이템 유효성, 쿨다운, 소모/교체 등을 기존 서버 권한으로 최종 판정. 임의 '성공' 상태를 클라이언트가 확정하지 않는다.
4. **실패/종료**: 인형 미보유, 아이템 삭제·교체, 수동 해제, 접속 종료, 상태 변화, 서버 거부 후 재시도 폭주 방지. 이벤트마다 무조건 아이템 사용 패킷 반복 금지.

### 이식 가능 여부 판단

- **독립 DLL 구현 가능성**: 충분. 이미 검증한 로직의 상태값·분기를 x86 DLL로 구현하고 구버전 아이템 사용 함수를 연동할 수 있다.
- **원본 기계어를 그대로 DLL로 떼어 내는 방식**: 구버전 클라이언트 객체 레이아웃, 인벤토리 및 이벤트 ABI, vtable, 메모리 수명, 전역 객체가 다를 수 있어 바로 작동하지 않는다.
- **서버 패킷 신규 구현**: 현 단계에선 필요하다고 확인된 근거가 없다. 먼저 구버전 클라이언트의 기존 아이템 사용 명령과 연결하여 검증해야 한다.

## 10. 검증 상태 / 후속 역분석

| 항목 | 상태 |
|---|---|
| 사용자 옵션 ON/OFF 토글, +0x14 저장 | **기계어 재확인** |
| 소환 이벤트 0x13/0x95 핸들링 | **기계어 재확인** |
| 옵션/소환 관련 상태 결합 후 아이템 사용 | **기계어 재확인** |
| 마지막 아이템 ID 저장·삭제 (+0x18) | **기계어 재확인** |
| 인벤토리 조회, 타입 0x49, 0x00B20E60 호출 | **기계어 재확인** |
| 기존 아이템 사용 함수에서 0x96 전달 / 0x00E717A0 호출 | **기계어 재확인** |
| 0x13/0x95/0x52/0x5C/0x49의 정확한 게임상 의미 | **미확정** |
| 실제 네트워크 opcode, 직렬화, 서버 수신 처리 | **미확정** |
| 구버전 x86 DLL 실클라이언트 연동 | **미구현·미검증** |

**다음 분석의 핵심**: \`0x00AC3DF0\`과 \`0x00E717A0\`을 따라가 실제 패킷 직렬화 및 최종 TCP 송신 호출을 확인한다. 그다음 구버전 바이너리에서 기존 아이템 사용 함수의 대응 주소와 calling convention을 찾아 연동한다.

---

**요약:** MJBin 마법인형 자동소환은 단순히 별도 패킷을 찍는 기능이 아니라 **활성 설정 + 내부 이벤트 + 기존 인형 아이템 기억/상태 판단 + 아이템 사용 호출**로 구성되어 있다. 아이템 사용 루틴 재사용은 확인됐고, 실제 패킷 opcode는 아직 최종 추적되지 않았다.

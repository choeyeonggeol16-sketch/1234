## 3. 연구 ① — 물리 명중률 5~95% 상·하한 폐지 여부

### 3.1 일본 실험의 직접 관측값

| 실험 | 일본 서버 조건 | 공격 횟수 | 명중 | 관측률 |
|---|---|---:|---:|---:|
| A | 공격 LV86 환술사(STR14, +9 명상 지팡이) → 방어 LV14 기사(AC+7) | 620 | 620 | **100.0%** |
| B | 공격 LV6 기사(STR20, 수련자의 검) → 방어 LV82 다크엘프(AC-102) | 1,000 | 0 | **0.0%** |

기존 시스템에서 물리 명중 확률을 5~95%로 제한한다는 가정이면:

```text
P(620회 전부 명중 | 실제 p=0.95) = 0.95^620  ≈ 1.5439573 × 10^-14
P(1000회 전부 빗나감 | 실제 p=0.05) = 0.95^1000 ≈ 5.2918227 × 10^-23
```

두 실험은 **5~95% 강제 제한 가정과 사실상 양립하기 어렵다.** 연구자는 개편 후 물리 명중률이 0~100% 구간을 가질 수 있다고 해석했다. 다만 유한 표본이므로 정확한 내부 코드가 수학적으로 0.0/1.0인지, 또는 아주 작은/큰 확률인지까지 직접 증명한 것은 아니다.

### 3.2 RKern 원본 코드에서 확정된 불일치

**`HitEvasionModel.java:7-8`**

```java
public static volatile double HIT_MIN = 0.05;
public static volatile double HIT_MAX = 0.95;
```

**`HitEvasionModel.java:121-125`**

```java
final double min = HIT_MIN;
if (hit < min) return min;
final double max = HIT_MAX;
if (hit > max) return max;
return hit;
```

`rollHit`은 이 값을 10,000단계 난수와 비교하므로 실제 명중 판정에 제한이 반영된다. 전체 Java 소스 검색에서는 `HIT_MIN/MAX`를 다른 곳에서 변경하는 코드가 발견되지 않았다.

**판정: 반드시 수정해야 할 명확한 버전 불일치.** 다만 `HIT_MIN=0`, `HIT_MAX=1`로 숫자만 바꾸는 것으로는 리뉴얼 후 명중 공식까지 복원되지 않는다. 곡선 내부가 sigmoid이기 때문에 극단 0%와 100%가 어떤 조건에서 가능한지까지 별도 검증해야 한다.

- 내부 H를 **134로 변경한 별도 감도 분석**에서는 데이터 적합도가 훨씬 좋아진다. **이 결과는 13 보정을 실제 서버에 넣으라는 뜻이 아니다.**
- `L1AttackHelper.calcPcHitH`의 `getBaseMeleeHitByLevelClass()`, `CalcStat.근거리명중(totalStr)`, `getHitup()`, `getHitRate()`, 무기 명중/강화 `weaponEnchant >> 1`, 무게 및 손상 페널티를 일본 표시 명중 147의 집계 방식과 대조해야 한다.
- 실제 상대의 DG, 장비, 스킬, 무게 등 원문에 명시되지 않은 변수는 격리 계산에서 0으로 설정했다. 따라서 이 비교만으로 **내부 H가 실제로 13만큼 잘못되었다**고 단정할 수 없다.

### 4.3 별도의 실질적 결함 — AC 64 미만 LUT 외삽

`HitEvasionModel.java`의 보간 기준 `AC_KNOT`은 **64,65,...,150**부터 시작한다. 그런데 `rebuildLut()`은 **AC 0부터 255까지** 값을 계산한다. 따라서 AC 0~63은 원 관측 기준점 밖으로 외삽된다.

원본 Java 클래스를 실행해서 얻은 예:

| 내부 H | 방어 AC 절댓값 | 계산 명중 확률 |
|---:|---:|---:|
| 0 | 0 | **95.0%** |
| 15 | 0 | **95.0%** |
| 30 | 0 | **95.0%** |
| 50 | 0 | **95.0%** |
| 0 | 64 | 60.4% |
| 30 | 120 | 6.39% |
| 30 | 150 | **8.59%** |

**문제 A: 낮은 AC에서 명중 0에 가까운 공격자마저 95%가 나오는 현상.** 이는 모델의 외삽이 실제 전투 규칙과 충돌할 수 있음을 보여 준다. 실제 `calcPcHitH`가 H를 0으로 만들 수 있으므로 도달 불가능한 값이라고 치부할 수 없다.

**문제 B: H=30에서 방어 AC -120 → -150으로 방어가 올라가는데도 명중률이 6.39% → 8.59%로 오르는 비단조 구간.** 이는 낮은 H의 스플라인·기울기 보간 조합을 따로 검사해야 함을 시사한다. ※ 2016 일본 원문은 해당 낮은 H의 AC 조합을 직접 측정하지 않았으므로, 본서버 위반 판정이 아닌 **모델의 내부 불변식 검증 실패**로 분류한다.

단순히 명중률의 최댓값·최솟값 제한을 제거하면 외삽 이상치가 더 크게 드러날 수 있다. **따라서 5~95% 제한 수정과 저AC 외삽 검증은 함께 검토해야 한다.**

## 5. 필수 작업 지시 — 최소 변경, 실측 기반

**우선순위 P0 — 명중률 경계**
1. 기존 5~95% 강제 제한을 실제 일본 리뉴얼 후 명중 정책과 일치시키는 방향으로 수정한다.
2. `rollHit`의 정수화, 0%/100% 판정 및 난수 `nextInt(10000)`의 경계를 함께 검사한다. 곡선을 그대로 두고 `HIT_MIN/MAX` 상수만 바꾸는 임시 처방은 **완료로 인정하지 않는다**.
3. PC→PC / PC→NPC / NPC→PC / NPC→NPC 공격 경로를 각각 확인하고, 근거리·원거리·스킬 예외를 보존한다.

**우선순위 P1 — AC 곡선 및 내부 H 정합성**
1. 일본 33,000회 공개 원자료를 회귀 기준으로 사용한다. 단일 AC 점을 기준으로 튜닝하지 않는다.
2. 일본 표시 명중 147의 정의와 RKern 내부 H 합산식을 항목별로 대조한다. H=134의 우수한 적합은 **문제 위치 탐색 근거**로만 사용하고 하드코딩하지 않는다.
3. AC 부호 처리(`Math.abs`), `AC_KNOT` 기준점, 0~63 외삽, 150~255 꼬리 구간, `S_MIN/MAX`, DG/ER 및 특수 회피 보정을 함께 점검한다.
4. 동일 공격 이벤트에 **명중/회피 판정 중복 호출**이 있는지 점검한다. 실제 중복 로직이 발견되면 단일 권위 경로로 통합·삭제·수정하고 회귀 검증한다. 단, 서로 다른 정상 공격 유형 분기는 유지한다.
5. 실제 코드를 수정할 때 기존 CIO 소유 실행과 네트워크·CacheD·NPC 이벤트 순서를 보존하고, 불필요한 스레드·큐·객체 할당을 도입하지 않는다.

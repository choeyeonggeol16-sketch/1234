# RKern 송신 암호화와 Netty 고부하 측정

2026-11-21에 Linux 6.18.57 x86_64, Java 21.0.13에서 측정했다. 클라이언트와 서버는 같은 머신에서 CPU 쿼터 2개를 공유했다. Netty 버전은 4.2.21.Final이다.

## RKern 송신 암호화 전후

기준 소스는 `6a3473d`다. 적용 후에는 같은 빌드에서 `CUserSocket`과 `CPacketCryptor`의 행동 패킷 묶음 암호화 변경을 반영했다. 실제 게임 리스너에서 1,024개 연결, Selector 소유 스레드 2개, window 4로 설정했다. 각 요청은 암호화된 행동 프레임 32개를 받는다. 2초 준비와 4초 측정을 3회씩 교차 실행한 중앙값이다.

| 항목 | 적용 전 | 적용 후 | 변화 |
|---|---:|---:|---:|
| 처리량 (요청/s) | 91,213 | 94,634 | +3.8% |
| RTT p99 (ms) | 99.4 | 132.9 | +33.7% |
| RTT p99.9 (ms) | 159.8 | 162.2 | +1.5% |
| 서버 CPU/요청 (µs) | 6.61 | 6.03 | -8.8% |

독립 클라이언트 암호화 구현으로 응답 헤더, 암호문, 순서를 대조했다. 6회 모두 성공했고 송신 거부는 0건이다. 적용 후 처리량은 3.8% 증가했고 p99는 33.7% 길어졌다. 이 부하에서 p99 개선은 확인되지 않았다. [묶음 암호화 설계와 독립 측정](RKern_Opcode_Dispatch_Table_Optimization_Review_20261121.md#7-송신-행동-패킷-묶음-암호화-2026-11-21-추가-검증)

## 5,000개 연결에서 전송 계층 비교

TCP 프레임 에코를 공통으로 실행했다. 연결당 window 8, payload 256B, 소유 스레드 2개, 준비 1.5초, 측정 3초를 사용했다. 게임 암호화 적용 전후의 수치는 위의 별도 게임 리스너 실험에서 확인할 수 있다.

| 전송 방식 | 성공 회차 | 요청/s | p99 (ms) | p99.9 (ms) |
|---|---:|---:|---:|---:|
| RKern Java Selector | 3/3 | 142,927 | 480.2 | 484.4 |
| Netty Selector | 2/3 | 39,958 | 1,400.9 | 1,585.4 |
| Netty epoll | 2/3 | 64,685 | 857.7 | 1,111.5 |
| Netty io_uring | 0 | — | — | — |

Netty Selector 1회차와 epoll 3회차에서 클라이언트가 연결 리셋을 보고했다. 중앙값은 성공한 회차만 집계했다. 이 환경에서 io_uring의 링 생성은 `Operation not permitted`로 실패했다. [TCP 에코 측정 코드](../rkern/docs/jproring_linux_benchmark_20261120/run.py)

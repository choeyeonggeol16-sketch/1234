# RKern L1InventoryTransaction 189~191차 — 객체 할당·인벤토리 스캔 최적화

## 검증 범위
- 원본 188차를 기준으로 실제 생산 `debit(L1PcInstance,L1ItemInstance,int)`, `debit(L1PcInstance,int,int)`, `commitInternal()` 메서드를 각각 추출하여 Java 21 타입 컴파일 및 실행 비교.
- 단일 스택, 여러 스택, 기존 부분 차감, 부족한 수량, 장착 아이템, 오래된 참조, 정렬/역순/대량 DB 항목, SQL preimage 검증 실패, staging 예외, 커밋 후 반영과 release-before-effects 두 모드 검사.

## 189차: 부족한 수량 사전검증
`debit(pc,item,count)`는 거래에 아직 준비하지 않은 아이템의 수량이 부족하면, 기존과 동일하게 참조 동일성 및 소유권을 검증하고 `false`를 반환한다. 이 요청으로 인해 `Entry`, `ItemSnapshot`, 복사 이미지가 준비되지 않도록 한다. 이미 준비된 스택은 기존 이미지를 검증한다.

**의도적 차이:** 188차에서는 일부 실패한 직접 차감도 변경 없는 `Entry`를 만든 뒤 트랜잭션에 남겼다. 이제 이러한 실패는 아예 거래 행을 준비하지 않는다. 정상적인 호출자는 `false`를 거래 중단으로 처리하며, 검증 시 기존 코드의 그 불필요한 준비 행은 결과 비교에서 제외했다. 경제 DB 잠금 자체를 제거하는 성공 거래 변경은 아니다.

## 190차: 템플릿 차감 한 스택 경로
충분한 재고가 확인되면 즉시 preflight 루프를 종료하고, 첫 스택에 충분한 수량이 있으면 두 번째 전체 인벤토리 순회 대신 기존 `debit(pc,item,count)` 경로로 차감한다. 여러 스택에서 빼야 하면 이전의 인벤토리 순서대로 분배한다.

## 191차: 정렬된 다중 행은 복사 생략
`commitInternal()`의 SQL 행 순서는 반드시 row ID 오름차순이다. 배열의 준비 순서가 이미 오름차순이면 기존 배열을 읽기 전용 정렬 뷰로 활용하고, 역순/혼합 순서이면 `Arrays.copyOf()` 후 `Arrays.sort()`를 수행한다. 트랜잭션 제출 후 항목을 추가하는 행위는 기존 `submitted/open` 검사로 차단된다. DB 스냅샷과 커밋 후 아이템 replay용 복사는 유지한다.

## 실행 검증
- `test_debit_equivalence.py`: 실제 188차와 신규 생산 debit 메서드 Java 21 타입/동작 비교, **225,600개 조건 통과**. 신규 요청 수량 부족에서는 스냅샷/복사 0회, 오래된 객체 동일 예외, 한 스택 재고 충분 시 인벤토리 조회 2회→1회 확인.
- `test_commit_equivalence.py`: 실제 188차와 신규 `commitInternal()` Java 21 타입/동작 비교, **40,015개 조건 통과**. SQL preimage·쓰기·커밋 반영·잠금/격리와 실패 경계 유지.
- JDK 21 `JavacTask.parse()`로 원본 전체 소스 구문 검사 **1,923개, 오류 0**. 실제 외부 의존성 타입 확인/DB 실행과 별개.
- 기존 188차의 미변경 생산 Java, 문서, 테스트 및 native 자원은 내용 동일. `src` 생산 변경 1개.

## 보류한 위험한 최적화
`ItemSnapshot` 제거, 커밋 SQL 이미지와 replay 이미지 합치기, 완료 콜백 재사용·풀링은 하지 않았다. mutable 아이템 참조가 비동기 DB 단계와 충돌할 수 있으므로 실제 수명 분석 전에는 변경하지 않는다.

## 미검증
실제 MySQL 커밋/ACK loss/재시작/중복 거래, 전체 의존성 타입 컴파일, 실제 전투·인게임, JFR 할당률·GC 실측은 수행하지 않았다. 189~191차 최적화로 카드 복구·일반 강화 전체 원자성·펫 월드 생성 보상 등이 해결되지는 않는다.

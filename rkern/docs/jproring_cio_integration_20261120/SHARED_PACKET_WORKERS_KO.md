# RKern 수신 패킷 공유워커

공유워커는 실제 TCP 수신부터 프레임 복호화, 게임 opcode 핸들러 호출까지 실행한다. 워커가 바뀌어도 한 연결의 패킷과 그 캐릭터에 연결된 타이머·DB 완료 콜백에는 같은 논리 샤드가 지정된다. 한 번에 한 워커만 해당 샤드를 실행할 수 있다. 소켓의 송신 FIFO와 송신 암호화는 누적 서버 소스 `d6edf7a6`의 구현을 사용한다.

## 실행 방식

각 셀렉터의 대기 스레드가 준비된 소켓을 수집한다. 고정 개수의 패킷 워커는 FIFO에서 준비된 샤드를 하나씩 받아 게임 작업을 실행한다. 샤드마다 대기열에 들어갈 수 있는 작업은 하나다. 패킷마다 별도의 작업 객체나 수신 버퍼 사본을 만들지 않는다.

한 워커가 처리 중인 샤드에 계속 일이 있으면 여러 번 연속 진행할 수 있다. 다음 샤드가 기다리거나 4회 또는 약 1ms의 예산에 도달하면 준비된 샤드를 큐 뒤로 돌린다. 예산은 처리 단계 사이에 검사한다. 이미 시작한 핸들러를 중단하는 시간제한은 아니다. 셀렉터 대기, 게임 처리, 종료 정리는 같은 샤드에서 겹치지 않는다. 같은 샤드의 느린 핸들러 뒤에 놓인 작업은 계속 기다린다.

공유 모드에서 CPU 두 개를 노출하고 샤드 수를 자동 설정하면 논리 샤드 4개와 물리 패킷 워커 2개를 사용한다. 이때 준비 이벤트를 기다리는 스레드가 4개 더 있으며 기존 watchdog도 실행된다. `DisruptorShardCount`로 지정한 논리 샤드 수는 기존 설정 한도 안에서 유지한다. 단일 CPU 또는 단일 네트워크 샤드에서는 인계 비용을 피하도록 해당 샤드가 직접 실행한다.

## 검증 방법

- `SharedPacketWorkerRegression`은 암호화된 연결 4개에서 실제 워커의 스레드 신원과 논리 샤드 번호를 확인한다. 한 핸들러를 정지시킨 채 다른 샤드의 진행, 같은 샤드의 타이머·완료 콜백 직렬화, 뒤이어 도착한 패킷 순서, 종료 시 수신·송신 버퍼 반환을 검증한다.
- `SelectorCioIntegrationTest`는 실제 로그인 리스너의 기동·재기동, 최대 프레임 분할 수신, 암호화 FIFO, 종료 및 재접속을 검증한다. `BroadcastDeliveryRegression`은 기존 방송 및 송신 경로를 검증한다.
- `SharedPacketWorkerLoad`는 루프백 연결 6개 중 균등 부하는 전부, 편중 부하는 동일한 세 연결을 사용한다. 실제 인게임 opcode 디스패치에 연결한 시험용 핸들러가 정수 연산을 하고 암호화 응답을 보낸다. 요청별 응답 순서와 내용이 기대값과 일치해야 측정을 완료한다. 실게임 월드와 외부 DB는 이 부하에 포함하지 않았다.

## 병목과 지연 측정

하나의 핸들러를 약 200ms 멈춘 상태에서 다른 연결로 패킷 하나를 보냈다. 고정 워커 기본 설정에서는 두 연결이 샤드 0에 배치돼 두 번째 응답에 199.196ms가 걸렸다. 공유워커 기본 설정에서는 두 번째 연결이 샤드 2에 배치돼 0.663ms 만에 응답했다. 첫 핸들러가 끝나기 전에 두 번째 응답까지 도착했다. 이 비교에는 논리 샤드가 2개에서 4개로 늘어 같은 샤드에 배치될 가능성이 낮아진 효과가 포함돼 있다.

Linux, JDK 21, CPU 할당량 2개에서 서버와 부하 클라이언트를 함께 실행했다. 활성 클라이언트당 1,024회 예열 후 총 36,864개 요청을 보내고 각 연결에 미응답 요청을 최대 16개 유지했다. 아래 표의 처리량은 모드별 두 번의 산술평균이고 p99는 각 실행에서 클라이언트가 관측한 왕복 지연이다. 실행 순서는 고정, 공유, 공유, 고정이었다.

가장 비싼 편중 부하에서 공유 모드 처리량은 두 번 각각 13,991과 7,825 요청/초로 변동이 컸고 p99는 두 번 모두 늘었다. 짧은 핸들러에서 공유 모드의 논리 샤드도 고정 모드와 같은 2개로 지정해 한 번 더 측정했다. 편중 부하는 53,598 요청/초와 p99 4.60ms, 균등 부하는 55,867 요청/초와 p99 33.97ms였다. 같은 샤드의 느린 작업이 이웃 요청을 붙잡을 수 있다는 제약은 두 모드 모두에 적용된다.

## 기능 검증 및 설정

서버 Java 소스 1,698개와 시험 소스 5개를 컴파일했다. 실제 암호화 연결에서 패킷 순서, 워커 간 실행권 이전, 타이머·DB 완료 콜백의 순서, 로그인 리스너 재기동과 24회 연결 재설정·재접속을 확인했다. 방송에서는 중간 수신자 종료 후 나머지 499명 전송, 동시 생산자 4개의 640프레임 전달, 송신 버퍼 부족 및 단일 슬롯 경로를 검증했다. 종료 시 대여한 버퍼는 모두 반환됐고 방송 시험에서 JVM 교착이 감지되지 않았다.

셀렉터 자체의 소켓 종료, 메일박스 동시 접근, 타임아웃, 기동 실패 복구 시험도 통과했다. 로그인 리스너 시험에서는 JDBC 풀을 초기화하지 않아 CacheD가 DB 연결 실패 및 재시도를 기록했다. 샤드에서 완료 콜백이 실행되는 순서까지 검증했으며 실제 DB 저장 성공은 검증 범위 밖이다.

이 개발 브랜치의 기본값은 `-Drkern.network.sharedPacketWorkers=true`다. 기존 고정 모드로 비교하려면 서버 시작 시 `-Drkern.network.sharedPacketWorkers=false`를 지정한다. 측정 범위는 로컬 TCP와 시험용 게임 핸들러까지다. Windows 및 실제 게임 월드의 동접 1만 명에서의 처리량과 p99는 별도 측정이 필요하다.

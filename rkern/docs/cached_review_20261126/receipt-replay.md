# CacheD 커밋 직후 연결 종료와 저장 지연

2026-11-26 기준으로 직전 커밋 `4ec5747b`에서 남은 두 경로를 점검했다. 거래 영수증은 아이템 변경과 같은 DB 트랜잭션에 기록되는 고유 ID다. 같은 거래를 다시 요청해도 재지급하지 않으며, 서버는 이 영수증으로 DB 반영 여부를 확인한다.

## 연결이 끊긴 거래

DB가 커밋한 직후 연결이 끊기면 캐릭터가 먼저 퇴장해 이미 저장한 거래를 게임에 반영하지 못하는 경우가 있었다. 수정본은 연결을 즉시 닫고 새 거래 접수를 막는다. 기존 거래는 등록 당시의 캐릭터, 소켓, 세션 세대와 예약 토큰이 모두 일치할 때 원래 담당 스레드에서 마친다. 게임 내 수량과 후속 효과를 반영한 뒤 로그아웃과 최종 저장을 재개한다.

창고 단건·일괄 입출고, 일반 인벤토리 거래, 캐릭터 선택창 이동, 개인상점 연결 종료, 강제 퇴장과 서버 종료에 같은 거래 수명 규칙을 적용했다. 캐릭터를 교체한 뒤 잘못 도착한 응답이나 DB 결과를 확정할 수 없는 거래는 계속 격리한다. 정상 연결 종료를 처리하기 위해 DB 격리를 해제하지 않는다.

- 일반 거래에서 아이템 100개 중 7개를 차감했다. DB 수량이 93이고 기존 캐릭터의 수량이 아직 100일 때 실제 TCP 연결을 끊었다. 원래 캐릭터에서 93을 반영하고 후속 효과를 한 번 실행한 뒤 로그아웃했다. 새 세션이 DB에서 읽은 수량은 93, 거래 영수증은 한 건이었다. 같은 조건에서 직전 커밋은 캐릭터 유지 검사에 실패했다.
- 단일·복수 아이템 창고 맡기기와 찾기에서 DB 커밋과 게임 내 반영 사이에 소켓을 닫고 양쪽 보관 위치, 영수증 한 건, 후속 효과 한 번을 검사했다. 새 DB 스키마와 JVM으로 두 차례 모두 통과했다. [창고와 일반 거래 통합 테스트](../../tests/storage/WarehouseDisconnectRegression.java)
- 두 소유자가 관여한 예약 취소, DB 작업이 끝나기 전의 게임 측 완료 통지, 늦은 실패 통지에서 대기자가 한 번만 깨어나는지 검사했다. 완료 후 소유자 대기 목록이 비는지도 확인했다. [저장 대기열 테스트](../../tests/storage/CacheDQueueFencesRegression.java) · [게임 측 거래 수명 테스트](../../tests/trade_lifecycle/test_inventory_receipt_drain.py)

## 고부하 저장

영수증 테이블이 InnoDB인지 확인하고 거래 ID를 기록하는 작업을 SQL 한 문장으로 합쳐 영수증마다 DB 왕복을 한 번 줄였다. 거래 ID가 같을 때의 중복 처리, 소유자와 종류 확인, 커밋 응답 유실 시 별도 연결에서 영수증을 대조하는 절차를 유지했다. MariaDB에서 동시 중복 요청, 롤백, 커밋 응답 유실, 테이블 누락과 스토리지 엔진 변경을 검사했다. 스키마 변경은 필요 없다. [영수증 통합 테스트](../../tests/storage/CacheDReceiptClaimRegression.java)

Java 21과 격리된 MariaDB 11.8.9에서 DB와 JVM에 CPU를 하나씩 배정했다. 계정·캐릭터 저장과 거래를 고정 시드로 섞고, 800건 예열 뒤 한 행을 150ms 동안 잠갔다. 각 비교는 같은 부하를 기존 → SQL 수정 → 기존 → SQL 수정 순서로 실행했다. 실처리량에는 네 작업 유형이 모두 들어간다. p99는 잠긴 소유자와 무관한 거래가 발행 예정 시각에서 로컬 저장 완료까지 걸린 시간이다.

| 초당 요청 | 실행 | 실처리량, 기존 → 수정 | 독립 거래 p99, 기존 → 수정 |
| ---: | --- | ---: | ---: |
| 1,600 | 1차 | 1,137.1 → 1,182.4건/초 | 609.2 → 534.2ms |
| 1,600 | 2차 | 1,143.9 → 1,205.9건/초 | 599.2 → 491.3ms |
| 320 | 1차 | 320.0 → 320.1건/초 | 10.9 → 8.9ms |
| 320 | 2차 | 320.1 → 320.0건/초 | 8.1 → 18.8ms |

각 고부하 실행에서 2,400건, 각 320건/초 실행에서 1,600건을 전부 저장했다. 고부하 두 비교에서 실처리량은 4.0%와 5.4% 증가했고 독립 거래 p99는 12.3%와 18.0% 감소했다. 초당 320건에서는 지연 개선이 일관되지 않았다. 완료 후 잔액과 저장 순서를 대조했고, 남은 작업과 소유자 인덱스 및 검출된 JVM·InnoDB 데드락은 0건이었다. [실행별·구간별 측정값](receipt-stage-summary.csv)

연결 종료 수정까지 포함한 최종 코드로 같은 고부하를 한 차례 더 측정했다. **2,400건을 모두 저장했고 실처리량은 1,178.0건/초, 독립 거래 p99는 540.5ms**였다. 가장 느린 독립 거래 13건에서 큐 대기 중앙값은 538.4ms, DB 작업 중앙값은 2.0ms였다. 완료 시 남은 작업과 검출된 데드락은 0건이었다.

측정한 지연의 범위는 서버 내부 저장까지다. 초당 1,600건을 계속 넣으면 이 시험 환경의 처리 용량을 넘어 큐 대기가 남는다. 실제 Windows 게임 서버의 네트워크 왕복, Oracle MySQL 5.7 실행, 장시간 힙 추이와 전원 상실 뒤 메모리 전용 효과의 복구는 이번 시험 범위 밖이다.

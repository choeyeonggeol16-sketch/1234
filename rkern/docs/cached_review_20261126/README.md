# CacheD 저장 경로 재검수

2026-11-26에 기존 커밋 `c2cbecb5`와 수정본을 비교했다. 실제 DB 검증은 운영 데이터와 격리한 MariaDB 11.8.9에서 수행했다. 자바는 21버전을 사용했다. 이번 변경에 DB 스키마 마이그레이션은 없다.

아래 측정 이후 영수증 저장과 연결 종료 처리를 추가로 수정했다. [후속 검증과 고부하 비교](receipt-replay.md)

## 재현한 문제와 수정 결과

| 조건 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 다른 캐릭터 둘이 동시에 창고에서 아이템을 분리 출고 | 새 아이템 ID가 같은 기본 키 간격에 있으면 InnoDB 교착 오류 1213 발생 | 새 행은 고유 키가 보호하는 INSERT 한 번으로 생성. 두 출고가 모두 커밋됐다. 이미 사용 중인 ID는 원래 행을 보존하고 출고 전체와 영수증을 롤백했다. |
| 한 소유자의 SQL 행이 잠겼을 때 | 대기 작업 2,048건을 한 소유자가 채우면 무관한 소유자의 요청도 거절 | 전체 한도는 2,048건. 마지막 4자리는 관련 소유자 모두에게 대기 중 DB 작업이 없는 요청에 배정한다. 원래 행이 계속 잠긴 상태에서 독립 거래가 커밋됐고, 잠금을 풀자 기존 2,044건이 순서대로 저장됐다. |
| 커밋 결과가 불명확해 세 소유자를 격리한 뒤 새 요청 2,200건 유입 | 이미 격리된 소유자의 요청이 공용 큐의 남은 2,046자리를 소진 | 추가 요청 2,200건을 접수 전에 거절하고 기존 작업과 거래 순서를 보존했다. 무관한 소유자의 저장은 완료됐다. |
| DB 쓰기 중 아이템 수량이 10 → 9 → 10으로 변경 | 9가 저장된 뒤 메모리의 10을 이미 저장한 값으로 볼 수 있음 | SQL이 기록한 9를 기준으로 변경을 감지하고 다음 저장으로 10을 복구했다. 실제 테이블 구조의 임시 테이블에서 18개 개별 저장 비트, 복합 저장, 전체 저장을 검증했다. |
| 로그아웃 1,024건 대기 중 소유자가 알려진 아이템 256개 저장 | CacheD 공용 락에서 로그아웃 대기 목록 전체를 256회 순회 | 전체 순회 0회. 이전·현재 소유자를 개별 처리하고, 소유자 미상 아이템의 마지막 저장이 끝난 경우에만 전체를 다시 확인했다. |
| 아이템 즉시 저장 요청 및 재로드 | 즉시 저장이 기존 50ms 대기 만료를 기다릴 수 있었고, 재로드 중에는 새 소유자와 저장 작업이 겹칠 수 있었음 | 정상 항목은 즉시 실행 대상으로 전환한다. 실패한 항목은 재시도 간격을 지킨다. 재로드로 소유자가 바뀌면 기존 SQL 소유자와 새 소유자 양쪽의 작업 순서를 보장한다. |

인증 및 캐릭터 입장 조회는 소켓당 한 건씩만 진행한다. 이전 요청의 지연된 콜백은 새 요청을 해제할 수 없다. 서버 종료 시에는 CIO가 거래 완료를 처리할 동안 DB 접수를 유지하고, CIO 종료 뒤 후속 저장까지 비운다. 지연된 완료 처리와 그 직후 추가한 저장이 각각 한 번 실행되는지 검증했다.

## 메모리

기록용 아이템 스냅샷 8,000개를 유지하면서 외부에서 원본 아이템 참조를 해제한 뒤 GC를 실행했다. 계속 살아 있는 원본은 8,000개에서 0개로 줄었다. 스냅샷 8,000개의 ID와 수량은 모두 유지됐다. DB 재시도에는 스냅샷만 필요하며, 게임이 사용 중인 실물 아이템이 있으면 커밋 결과를 계속 반영한다.

캐릭터 연결 정보가 없는 계정 객체의 생성 시 할당량은 건당 488바이트에서 120바이트, 캐릭터 하나를 연결하는 경우는 592바이트에서 352바이트로 줄었다. 같은 JVM에서 `ThreadMXBean`으로 측정한 값이다. 장시간 운영 서버의 총 힙 사용량은 측정하지 않았다.

## 혼합 부하

고정 시드로 계정·캐릭터 저장과 거래를 섞었다. 매 실행에서 800건 예열 후 한 행을 150ms 동안 잠갔다. 독립 거래 p99는 발행 예정 시각부터 로컬 저장 완료까지의 시간이다. 클라이언트 왕복 지연은 별도 측정 대상이다.

| 초당 요청 | 측정 건수 | 기존 실처리량 | 수정 실처리량 | 기존 독립 거래 p99 | 수정 독립 거래 p99 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 320 | 1,600건씩, 기존·수정 교대 2회 | 320.1/s | 320.1/s | 4.5 / 8.7ms | 6.5 / 26.3ms |
| 1,600 | 2,400건씩, 기존 2회·수정 1회 | 1,144.7–1,198.6/s | 1,159.4/s | 534.8–631.5ms | 610.8ms |

320/s 교대 측정에서는 두 번 모두 수정본의 p99가 높았다. 별도의 CPU 경합 실행에서는 72.3ms도 관측했다. 1,600/s 고부하에서 수정본의 가장 느린 독립 거래 13건은 큐 대기 중앙값이 607.9ms, DB 작업 중앙값이 2.5ms였다. 이 조건의 처리량·p99 개선은 확인하지 못했다. 고부하 표의 수정본에서 최대 미완료 작업은 674건이었다. 혼합 측정 뒤 변경한 2,048건 포화와 아이템 재로드 경로는 별도 시험으로 검증했다. [실행별·구간별 측정값](stage-summary.csv)

부하 종료 후 계정·캐릭터 저장값, 거래 순서, 잔액을 대조했다. 남은 DB 작업, 준비 큐, 소유자 인덱스는 0건이었다. 수정본의 시험에서 검출된 JVM·InnoDB 데드락은 0건이다. 커밋 뒤 게임에 반영하기 전에 원래 세션이 사라진 거래는 해당 소유자를 격리한다. 이런 미해결 거래가 있으면 서버 종료가 저장 대기 상태에 머물 수 있으며 DB 기록 대조가 필요하다.

## 회귀 테스트

[저장 테스트 소스](../../tests/storage/)는 서버 클래스와 동일한 Java 21 클래스패스에서 실행한다. `CacheDQueueFencesRegression`은 `expedite`, `quarantine`, `release`, `reload`를 각각 새 JVM에서 한 번씩 실행한다. `CacheDOwnerDrainRegression`은 인자 없이 실행한다. `CacheDWarehouseInsertConcurrency`와 `CacheDAdmissionReserveRegression`에는 격리 DB의 JDBC URL과 사용자 이름을 전달한다. 두 테스트는 무작위 이름의 스키마를 생성하고 해당 스키마만 정리한다.

## 검증 환경과 범위

Java 21, 누적 서버 운영 소스 1,696개, 격리한 MariaDB와 합성 로그인 세션을 사용했다. 여덟 PC 클래스, NPC, 레벨 1·50·51·89·90·99, 여섯 기본 스탯의 경곗값, 실제 장착 처리와 스킬 보정, 동시 원천 변경을 시험했다. 테스트 SQL은 임시 스키마에서 실행했다. 실제 게임 클라이언트에서의 화면 표시, 배포 아이템 전체의 모든 강화·축복·세트 조합, 실서비스 동시접속, 장시간 운영 힙 추이는 이번 시험 범위 밖이다. 여러 스탯을 다른 스레드에서 따로 읽을 때 동일 시점의 전역 스냅샷을 보장하지 않는다. [교차 검증](CreatureStatCrosscuttingRegression.java) · [반복 성능 측정](CREATURE_STAT_AB_20261127_KO.md)

- 운영 소스 1,696개가 Java 21에서 컴파일됐다. 기존 스탯 회귀 스크립트 15개와 수정본 서버 객체 생명주기 단언 121,087건이 모두 통과했다. 여기에는 PC·NPC의 HP·MP 전이 240,000건과 성장·초기화 검사가 포함된다.
- 실제 MariaDB에서 일반 스탯 투자와 재분배 후 지연 도착한 과거 스냅샷을 거절하고, 새 스냅샷을 저장해 여섯 스탯을 복원했다. 엘릭서 저장 검사는 운영 스탯 SQL과 영수증 처리를 사용하며, 소비 수량은 격리 테스트 테이블에 기록했다. 영수증 커밋 응답 유실과 동시 재시도는 공통 저장 경로에서 별도로 확인했다. 기존 카르마 영수증 회귀 226건도 통과했다. [영수증 검사](../../tests/storage/CacheDReceiptClaimRegression.java)
- 별도의 합성 TCP 세션에서 실제 아이템 사용 핸들러 `CS_ItemUse`를 실행했다. 레벨 55, STR 17 캐릭터가 엘릭서 2개 중 1개를 사용한 뒤 DB와 캐릭터 모두 STR 18, 기본 STR 17, 엘릭서 사용 횟수 1, 남은 수량 1이었다. 영수증은 한 건이었고 같은 레벨에서 두 번째 사용은 거절됐다. 이 격리 환경에는 별도 Pride 설정 파일이 없어 해당 아이템 목록 초기화 중 경고와 예외 로그가 발생했다. 엘릭서 적용과 DB 검사는 통과했다.
- 일반 레벨 포인트 투자와 재분배는 기존 CacheD 비동기 저장을 쓴다. DB 커밋 전에 프로세스가 종료되면 마지막 미저장 변경이 유실될 수 있다. 엘릭서의 아이템 차감·스탯 증가·영수증은 하나의 SQL 트랜잭션을 사용한다.
- 버프 한 번 적용·해제의 JVM 측정에서 할당은 240→248 B/op였고 5쌍 모두 CPU 시간이 늘었다. 전투 수치 조회는 두 빌드 모두 0 B/op였다. 수정의 목적은 누적·해제 값과 패킷의 정합성이며, 서버 전체의 부하 개선 여부는 운영 부하 측정이 필요하다.

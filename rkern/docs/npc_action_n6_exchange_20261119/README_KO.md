# NC NPC Action N6 개별 제작·교환 및 이동 안전성

기준: `RKern_NPC_Action_N3_N5_CommonCraft_Receipt_FULL_SRC_20261119.zip`.

## 변경 사항
- `NpcExchangeCommands` (신규): 조우의 돌골렘(200201) 무기 교환 A–F, 유리에(900135) 하딘/오림 일기장 복원 d/e, 엘릭서 룬(7000055, 7000054) A–E, 카뮤(200007) 무작위 프리즘, 달나라(900106) 아이템 구매. 총 20개 경제 명령을 기존 `L1InventoryTransaction`에 연결한다. 별도의 AtomicJob 구현, 워커, 큐, DB 엔진 없음. 성공 응답은 receipt replay 및 participant gate 해제 뒤 기존 owner에서 처리한다. 실패 시 원래 실패 페이지를 사용한다. 보조 디스패처 기존 우선순위 유지. 완료 콜백은 NPC 객체 대신 object ID, 보상명, 페이지 등만 저장한다.
- 조우의 돌골렘 A는 원래 41246 30,000개 소지 조건과 3,000개 실제 차감으로 서로 다르므로 원래 정책을 유지했다. B–F는 30,000개 차감. 기존 무기 +7 조건, 보상 ID와 페이지 순서 동일. 자료 없이 임의로 가격을 변경하지 않는다.
- 재료 선택은 기존 첫 일치 +7 무기 객체, 첫 스택, 비스택 아이템의 낮은 강화 우선(동일 강화는 목록 순서)을 유지한다. 착용 아이템 debit은 기존 트랜잭션 정책으로 실패하며 기존 비스택 선택과 달리 착용 아이템은 선택하지 않는다. 운영 아이템 템플릿에 따른 stack merge 및 속성 초기화/수량/용량 정책의 차이는 실서버 검증 필요.
- 카뮤 프리즘 4종은 원래 공유 RNG의 nextInt(4) 및 보상 ID 순서를 유지한다. 성공 이름을 얻으려고 ItemTable.createItem을 별도 호출하던 지점을 제거한다. 이 API는 L1World.storeObject를 호출하지만 원래 이름 전용 객체에는 회수 호출이 없었다. 이제 receipt의 보상 이미지에서 1개 표시 이름을 얻으므로 메시지 전용 월드 등록 객체를 만들지 않는다. 실패 경로의 RNG 소비는 준비 실패 단계에 따라 이전과 달라질 수 있다. 보상 목록·정상 확률은 동일하다.
- `CS_NpcAcion2`: 두 유료 이동(1000001 / 81210)에서 미등록 명령을 좌표 0,0으로 보내거나 과금하지 않는다. 원래 목적지 및 가격 유지. 활성 50015 PC방 이동, 7320260/522 유료 버프에서 기존 consumeItem 반환값도 확인한다. 일반 consumeItem의 영속 확정 자체를 보장하는 변경은 아님. 50015 후반 중복 분기(도달 불가 후보)는 이전 동작 보호를 위해 활성화하지 않았다.
- 두 버프 스킬 배열을 private static final로 재사용한다. 기존 호출 순서와 값은 변경하지 않는다.
- `HtmlCmdHandler`: 두 NPC 교환 호출부만 교체한다. 공통 제작, 대상 우선순위, 기존 XML 및 다른 명령을 변경하지 않는다.

## 검증 및 제한
- test_exchange.py: 실제 생산 신규 실행부를 Java 21에서 typed fake 인벤토리/transaction/packet으로 컴파일하고 검증. 28,662개 조합(재료·강화·착용 조건, 준비 실패, grant 실패, commit 거부, rollback, 성공 메시지, RNG, 레벨, 잘못된 명령/유료 이동) 통과. 원래 조합 ID/수량, 분기 대상, 이동 좌표 대응도 검사. 실제 DB 트랜잭션을 실행한 테스트가 아니다.
- 직전 N3 범위 테스트 1,324개 통과.
- Java 구문 1,925개 오류 0건. 전체 컴파일은 기존과 동일하게 531 errors / 5 warnings로 실패(외부 의존성 누락 등); 이전 로그와 바이트 동일. 통합 빌드 성공으로 간주하지 않는다.
- 기존 아이템 회귀 결과는 item_regressions.log 참조.
- 이번 범위의 SQL 실패/unknown commit/session replay 처리에는 기존 CacheD 및 L1InventoryTransaction의 처리 계약을 사용한다. 재접속 후 이전 NPC 페이지 응답, 대화 채널 수명, 실제 DB/인게임/JFR 및 장시간 retained heap 검증은 미수행.
- XML MakeItem/ListedAction은 동기 HTML 반환과 후속 액션 순서가 결합되어 있다. 별도의 continuation 계약을 검증하기 전까지 임의로 비동기 전환하지 않는다. 기존 미완료 XML 제작, 개별 보조 NPC 로직, TalkChannelCache 등의 단계는 남아 있다.
- NPC 전투 AI, 네트워크, 방송, 아이템 사용 코어, CacheD 구현은 변경하지 않았다.

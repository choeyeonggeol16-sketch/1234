# CacheD와 Net DB의 5,120명 동시 접속 시험

## 시험 범위

Java 21에서 합성 클라이언트 5,120개가 같은 호스트의 서버에 실제 TCP 연결을 열었다. 각 클라이언트는 서버의 초기 키를 받고 암호화된 프레임으로 요청을 보냈다. 서버는 연결마다 서로 다른 합성 계정과 캐릭터를 로그인 레지스트리, 월드, CacheD에 등록했다. 시험 콜백이 준비된 계정으로 입장시키므로 비밀번호 인증, 맵 가시성, 전투, NPC AI, 실클라이언트 렌더링 비용은 측정 범위에서 빠진다.

DB는 기존 Net 테이블 정의를 복제한 임시 스키마에 합성 계정과 캐릭터를 각각 5,120개, 인벤토리 행을 40,960개 넣었다. 거래는 CacheD의 실제 영수증 커밋 경로를 거쳐 두 합성 잔액 사이에서 1씩 이동한다. 종료 시 기대 잔액과 커밋된 거래 ID를 개별 대조한다. 창고·상점 클라이언트 화면 동작은 이 시험 범위에 포함되지 않는다.

## 부하 조건과 큐

서버와 클라이언트 JVM, MariaDB는 같은 Linux 호스트의 2 CPU 할당량을 공유했다. CIO 소유 스레드는 2개, CacheD 워커는 4개, JDBC 풀 상한은 8개다. MariaDB 11.8에서 InnoDB의 커밋 시 로그 동기화 설정은 1이었다. 보통 구간에는 응답 확인용 에코가 약 70% 포함되며, 계정·캐릭터 저장, 로그인용 계정 조회, 인벤토리 조회, 아이템 저장과 거래 영수증이 나머지를 구성한다. 저장 완료를 기다리는 시험용 스레드 6개의 대기열도 CacheD 접수 큐와 별도로 측정했다.

기준 커밋 `f26d30fb`과 수정본을 새 JVM에서 번갈아 두 번씩 실행했다. 각 실행은 5,120명이 모두 요청을 보낸 첫 구간, 1,024명이 반복 요청하는 구간, 1,024명이 160ms에 요청을 집중시키고 한 거래 행을 150ms 동안 잠그는 구간, 회복 구간을 거쳤다. 매회 요청 11,264개와 고유 거래 영수증 1,594개가 일치했다.

| 짧은 비교 | 1차 기존 → 수정 | 2차 기존 → 수정 |
| --- | ---: | ---: |
| 첫 5,120명 p99 RTT | 80.6 → 1,742.3ms | 60.0 → 52.8ms |
| 1,024명 반복 p99 RTT | 11.2 → 5.3ms | 9.0 → 84.0ms |
| 1,024명 집중 부하 p99 RTT | 393.2 → 395.4ms | 405.6 → 388.6ms |
| 집중 부하 실처리량 | 1,849 → 1,830건/초 | 1,806 → 1,848건/초 |
| 회복 구간 p99 RTT | 5.13 → 3.63ms | 4.89 → 4.32ms |
| 기존 5,120명 유지 중 미인증 연결 256개 접속·종료 | 281.3 → 75.4ms | 253.3 → 91.0ms |

수정본 1차의 첫 구간에서는 DB 대기 작업이 최대 275개, 시험용 저장 완료 대기열이 327개 쌓였다. 같은 수정본 2차의 첫 구간은 각각 28개와 9개였다. CPU 제한과 큐 적체가 함께 관측됐으며, 단일 원인은 확인되지 않았다. 두 차례의 집중 부하에서도 p99 개선 방향이 엇갈렸다.

### 전체 인원 60초 반복

모든 연결이 4초마다 한 번씩, 15회 작업해 각 버전에서 76,800건을 완료했다. 이 구간의 실처리량은 양쪽 모두 초당 1,280건이었다. 기존 → 수정 순으로 혼합 p99는 4.923 → 5.124ms, 예정 송신 시각 기준 p99는 5.910 → 6.027ms였다. 거래 영수증은 8.709 → 8.503ms, 인벤토리 조회는 6.861 → 6.304ms, 아이템 저장은 9.446 → 10.669ms였다. 이 비교는 수정본을 먼저 실행했다. 전후 구간을 포함해 버전별 영수증 10,811개와 최종 잔액이 일치했다.

### 전체 인원이 DB를 요청하는 경우

수정본에서 에코를 제외하고 5,120명이 2초에 걸쳐 각자 DB 작업 1건을 요청했다. 거래·계정 저장은 각 854건, 캐릭터 저장·계정 조회·인벤토리 조회·아이템 저장은 각 853건이었다. 5,120건 전부 응답했으며 발행은 초당 2,560건, 마지막 응답까지의 실처리량은 초당 1,261.7건이었다. p50은 1,133.5ms, p99는 2,992.3ms였고 발행 종료 후 2,058.1ms에 작업이 모두 끝났다. 이때 CacheD 작업 수의 표본 최댓값은 1,188개였고, 별도의 시험용 저장 완료 대기열은 2,422개였다. CacheD 상한 2,048개에 먼저 도달한 결과로 해석할 수 없다.

대기 원인을 더 좁히려고 시험용 저장 완료 대기 스레드를 6개에서 24개로 늘리고 CacheD 워커 4개 → 6개 → 4개 순서로 비교했다. 같은 전원 DB 부하에서 다음 결과가 나왔다. 워커 6개의 처리량과 지연이 두 대조군 범위 안에 있었고, 대기도 남아 배포본에는 기존 워커 4개를 유지했다.

| CacheD 워커 / 시험용 대기 스레드 | 실처리량 | p99 RTT | CacheD 대기 표본 최대 | 시험용 대기열 표본 최대 |
| --- | ---: | ---: | ---: | ---: |
| 4 / 24, 1차 | 1,132.5건/초 | 3,299.5ms | 1,399 | 2,215 |
| 6 / 24, 실험 | 1,152.1건/초 | 3,195.1ms | 1,240 | 2,149 |
| 4 / 24, 2차 | 1,231.8건/초 | 2,908.2ms | 1,216 | 2,185 |

시험용 대기열에는 실제 저장 완료를 기다렸다가 클라이언트에 응답하는 작업이 포함된다. 각 수치는 마지막 응답까지의 관찰값이며 운영 DB만의 지연이나 장기 최대 처리량을 뜻하지 않는다. 매 실행 후 잔액과 영수증을 확인했고 CacheD 대기 작업, 살아 있는 연결·월드 세션 및 대여 중인 다이렉트 버퍼는 0이었다. 60초 측정에서 관측하지 못하는 장기 누수와 간헐적 정지는 별도 문제다.

작업별 p50·p99, 예정 시각 기준 p99, 요청 수와 큐 표본, 구간별 메모리는 [부하 측정표](population-phases.tsv)에 있다. 세션·거래·데드락 집계는 [실행별 결과](socket-lifecycle.tsv)에 있다. A1·A2는 기존, B1·B2는 수정본이다. diag 표기는 워커·시험용 대기 스레드 수를 조절한 진단 실행이다.

## DB 쿼리와 스키마

MariaDB 실행 통계에서 계정 조회는 호출당 1행, 인벤토리 조회는 8행, 인벤토리와 보스 열쇠 조인은 10행을 검사했다. 계정·캐릭터·아이템 갱신과 거래 잔액 갱신은 각각 1행을 검사했다. 실행 계획에서도 계정 로그인 고유 키, 캐릭터별 인벤토리 키, 열쇠 및 거래 영수증의 기본 키 사용을 확인했다. 거래 커밋을 포함하는 JDBC 자동 커밋 전환이 네 실행에서 누적 SQL 시간이 가장 컸다. 이번 시험 결과에 따라 기존 Net 테이블, 인덱스, 트랜잭션 내구성 설정과 큐 상한은 유지했다.

## 변경한 경로

- 인벤토리를 읽는 도중 잘못된 아이템 행을 만나면 이미 읽은 행의 소유자만 캐시에 남았다. 이제 아이템과 보스 열쇠 조회 및 JDBC 자원 반환이 성공한 뒤 소유자를 등록한다. 기존 인벤토리의 소유권 변경과 저장 대기 순서를 유지하며 공용 잠금 한 번에 최대 64개를 처리한다.
- 아이템 저장이 이미 큐에 있으면 소유자, 원본 객체, 실제 저장 값과 요청 열을 확인한다. 기존 스냅숏이 요청을 포함하면 그대로 사용한다. 값이나 객체가 바뀌면 새 상태를 기록하고, 워커가 처리 중인 요청 뒤의 저장도 보존한다.
- 로그인 레지스트리에 등록한 키를 해당 소켓에 보관한다. 인증 전에 끊긴 연결을 정리할 때 전체 계정 순회를 없앴고, 계정 객체가 소켓에 게시되기 전에도 같은 계정의 두 번째 연결이 첫 번째 예약을 가져갈 수 없게 했다. 일반 로그인은 남은 정원을 원자적으로 예약한다. 실제 TCP 연결 7개로 정원 2개를 동시에 요청했을 때 정확히 2개가 승인됐고 GM 예외도 통과했다.

## 메모리와 세션 정리

대기 중인 아이템 5,120개를 네 스레드가 20번씩 다시 저장했다. 요청의 75%가 이전과 같은 상태일 때 생산자 스레드의 할당량은 요청당 168.01바이트에서 42.01바이트로 줄었다. 모든 요청에서 값이 바뀌는 대조군은 두 버전 모두 약 168바이트였다. 측정에는 Java ThreadMXBean의 스레드별 할당량을 사용했다. 이 수치는 전체 JVM 메모리 사용량과 구별된다.

로그인 등록 5,120개에서 미인증 소켓 하나의 레지스트리 정리 비용을 따로 측정했다. 기존 27.4~28.6µs와 호출당 144바이트에서 수정 후 39~60ns와 0바이트가 나왔다. 두 측정 모두 해당 로거를 껐다. 등록 키 참조 하나가 추가돼 이 JVM에서 소켓 객체 자체는 560바이트에서 568바이트로 커졌다.

## 저장 오류 및 포화 검증

실제 MariaDB에 정상 아이템 한 행 뒤에 잘못된 행을 넣어 읽기 실패 후 두 행 모두 캐시에 게시되지 않는지 확인했다. 보스 열쇠 매핑 조회가 실패해도 같은 결과가 나왔고, 복구한 뒤 아이템 65개와 열쇠 값이 정상으로 돌아왔다. 소유자가 바뀐 저장 대기 아이템 256개로 이전 소유자와 새 소유자의 저장 완료 경계도 검사했다.

별도 포화 시험에서는 DB 행 잠금을 유지해 공유 슬롯 2,044개와 독립 소유자용 예비 슬롯 4개를 모두 채웠다. 다음 요청은 접수 단계에서 거절됐고, 잠금 해제 후 접수한 작업은 1,256.2ms 만에 처리됐다. 재접수까지 확인한 동일 소유자의 갱신은 정확히 2,045회였으며 최종 대기 작업과 검출된 데드락은 0이었다.

## 재현

서버를 Java 21로 컴파일한 뒤 같은 클래스패스로 아래 시험 파일을 함께 컴파일한다. 실행은 비어 있는 작업 디렉터리에서 한다. Linux에서 한 프로세스가 TCP 양쪽을 소유하므로 파일 디스크립터 한도를 16,384 이상으로 맞춘다.

```sh
javac --enable-preview --release 21 -encoding UTF-8 -cp "$SERVER_CP" -d "$TEST_CLASSES" \
  rkern/docs/jproring_selector_transport_20261120/SelectorTransportTest.java \
  rkern/tests/storage/CacheDNetMixedLoad.java \
  rkern/tests/network/CioSyntheticPopulation.java \
  rkern/tests/network/CacheDCioPopulationLoad.java
```

`SERVER_CP`에는 빌드된 서버 클래스, 해당 서버의 라이브러리, MariaDB JDBC 드라이버를 넣고 `TEST_CLASSES`는 별도 디렉터리로 지정한다. 실행 전 `RKERN_BENCH_JDBC`, `RKERN_BENCH_USER`, `RKERN_BENCH_PASSWORD`, `RKERN_BENCH_REFERENCE_SCHEMA`를 격리된 시험 DB에 맞춘다. 시험은 임의 식별자의 새 스키마를 만들고 종료 시 삭제한다. 기준 스키마에는 Net DB의 테이블 정의가 필요하다.

```sh
java --enable-preview -ea -Xmx1536m -XX:ActiveProcessorCount=2 -Duser.timezone=UTC \
  -cp "$TEST_CLASSES:$SERVER_CP" CacheDCioPopulationLoad 5120 1024
```

장시간 반복에는 JVM 옵션 `-Drkern.population.soakRounds=15`를 추가한다. 전체 인원이 DB를 요청하는 구간은 `-Drkern.population.allStorage=true`로 켠다. 시험용 저장 완료 대기 스레드는 `-Drkern.population.observers=24`로 바꿀 수 있다. 매회 비어 있는 새 작업 디렉터리를 사용한다. p99 RTT는 클라이언트의 실제 송신부터 검증된 응답까지이며, 예정 송신 시각 기준 p99에는 클라이언트 발행 지연도 포함된다. 계정·캐릭터·아이템의 저장 응답은 해당 저장 완료를 확인한 후에 보낸다.

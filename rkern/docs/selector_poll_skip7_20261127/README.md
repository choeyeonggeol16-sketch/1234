# Java 21 Selector 폴링 생략 후보 검증 · 2026-11-27

**결정: 누적 서버의 기존 Selector 폴링을 유지한다.** Linux에서 5,000개 연결이 응답을 하나씩 기다리면 후보의 처리량이 10.4% 늘고 RTT p99가 35.9% 줄었다. 그러나 각 연결이 8개씩 몰아 보내면 Linux에서 세 번 모두 처리량이 줄고 p99가 늘었다. Windows에서도 8개 묶음의 중앙값이 같은 방향이었다. 고부하 이득과 꼬리 지연을 함께 요구하는 원 보고서의 채택 조건을 충족하지 못했다.

## 구현과 검증 범위

- 비교 기준은 서버 누적 브랜치의 `b29bf3b3`, 후보는 `f13a564c`다. 운영 코드 차이는 `CSelectorTransport.java` 한 파일이다. 소유 스레드는 대기 중인 I/O 또는 accept가 있으면 폴링을 연속 최대 7회 생략하고, 8번째 기회에는 새 커널 준비 이벤트를 수집한다. `advance()`와 `awaitWork()`는 같은 카운터를 사용하며 실제 폴링이 반환될 때 초기화한다. 메일박스만 준비된 경우에는 폴링을 수행한다.
- Java 21에서 1,694개 운영 소스를 컴파일했다. Linux에서 TCP·메일박스·암호화 FIFO·분할 프레임·송신 거부 격리·동시 방송·타이머 회귀를 확인했다. 새 테스트에서 대기 중인 쓰기가 계속될 때 신규 접속과 읽기 처리, 타이머 및 메일박스 진행, 7회 상한을 확인했다. Linux 후보는 5회 통과했다. 기준선은 첫 생략을 기대하는 단정에서 기존 동작대로 즉시 폴링했다.
- 작은 송신 버퍼를 사용해 실제 부분 송신을 유도했다. `OP_WRITE` 등록·해제, 읽기 일시 정지·재개, 잔여 데이터 전송 후 FIN, 타임아웃과 연결 리셋 시 대기 작업 취소를 확인했다. 종료 시 검사한 버퍼 대여와 대기 작업이 0이었고 JVM 데드락 검사는 통과했다.
- 실제 `CIOServer`와 별도 Java 부하 클라이언트를 같은 호스트에서 루프백으로 연결했다. 서버는 CIO 소유 스레드 2개를 사용했다. 암호화된 요청의 순번과 응답 바이트를 검증하는 테스트 콜백을 사용했다. DB, 월드 시뮬레이션과 실제 인터넷 지연은 측정 범위 밖이다. Linux는 서버와 클라이언트를 각각 CPU 0과 1에 고정했고 Windows는 호스티드 러너에서 같은 설정으로 두 빌드를 비교했다.
- W1은 한 연결에서 응답을 받은 후 다음 요청을 보낸다. W8은 최대 8개를 한꺼번에 보낸다. 표는 같은 환경의 기존 → 후보 순서이며 여러 쌍은 지표별 중앙값이다. 고정 전송률 조건의 처리량은 측정 기한 내 응답 수, RTT는 실제 송신 시각부터의 지연이다. 예약된 송신 시각 기준 지연, 누락된 송신 기회, 연결별 진행, 타이머 지연, 서버 프로세스 CPU와 JVM 할당량은 원시 JSONL에 담았다.
- 기본 행렬은 새로 시작한 JVM에서 프로필별 1.2~2.5초 예열 후 2.2~3.8초 측정했다. 지속 시험은 5,000개 중 1,000개 연결이 활성인 조건에서 각 빌드를 60초간 측정했다. 짧은 시험에서 얻은 p99.9와 부하 중 신규 접속 지연은 표본 수와 호스트 스케줄링의 영향을 받는다.

Linux의 W8 기본 두 쌍에서 처리량은 각각 76,036 → 74,782, 89,547 → 83,144 요청/초였다. 두 번째 후보 실행에서는 5,000개 중 4,999개 연결에 측정 구간 안에서 시작해 끝난 응답이 있었다. 이 수치는 측정 경계를 걸친 응답을 제외한다. 이 관측 하나로 데이터 유실을 판정할 수 없다.

**별도 재측정.** 5,000개 연결 W8을 4초 예열하고 8초 측정한 결과는 131,089 → 114,330 요청/초(−12.8%), p99 536.46 → 713.56 ms(+33.0%), p99.9 541.42 → 758.49 ms(+40.1%)였다. 이 회차에서는 양쪽 모두 5,000개 연결이 측정 구간 안에 응답을 받았다. CPU·할당량이 줄어드는 일부 측정에서도 응답 시간과 처리량은 악화됐다.

단일 연결은 첫 실행의 편차가 커 2.5초 예열·4초 측정으로 조건별 두 쌍을 추가했다. 무제한 W1의 p99 중앙값은 0.148 → 0.128 ms였다. 초당 192개를 예약한 조건은 약 191 요청/초로 비슷했고 p99는 3.291 → 3.404 ms였다. 초기 단일 연결 결과만으로 저부하 퇴행을 단정하기 어렵다. [Linux 재측정 원자료](measurements/linux-low-repeat.jsonl) · [Linux W8 재측정 원자료](measurements/linux-burst-repeat.jsonl)

## 폴링과 자원 회수

- 양쪽 OS의 각 빌드가 60초 혼합 부하에서 예약된 76,800개 응답을 모두 기한 안에 완료했다. 서버가 거절한 송신은 0건이었다. Linux의 이 조건에서 RTT p99는 4.419 → 3.838 ms였고 p99.9는 14.213 → 18.162 ms였다. Windows의 p99는 0.307 → 0.220 ms였다. 이 시험은 장시간 운영 중의 모든 누수를 보증하지 않는다.
- 별도로 계측한 5,000개 연결 W8 한 쌍에서, 측정 구간 안에 완료한 클라이언트 응답 1,000개당 Java Selector 호출 수는 Linux 147.74 → 109.24, Windows 238.50 → 126.66이었다. 양쪽에서 최대 생략 7회와 강제 재폴링을 관측했다. 수치는 Java API 호출 횟수다.
- W8에서는 측정 경계를 걸치는 요청이 많다. Linux에서 서버 소유 스레드가 같은 계측 구간에 송신을 수락한 응답을 분모로 삼으면 호출 수는 96.78 → 93.87회/1,000개(−3.0%)였다. Windows 계측에는 이 분모가 없다. 계측 실행은 처리량·지연 표에서 제외했다. [Linux 카운터](measurements/linux-probe.jsonl) · [Windows 카운터](measurements/windows-probe.jsonl)

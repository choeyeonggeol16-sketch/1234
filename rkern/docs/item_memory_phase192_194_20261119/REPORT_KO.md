# 192~194차 메모리 최적화 검증 보고서

## 경로

1. `transfer(from,item,count,to)`의 신규 행 준비 전 소유권·객체 참조 동일성·수량 부족을 검사한다. 이미 준비된 행은 `Entry.image`의 남은 수량으로 재검증한다. 성공 시 기존 `entry()` 및 아이템 이전 경로를 그대로 실행한다. 부족한 수량을 이전하려는 경우 이전 코드에서는 Entry·ItemSnapshot·detached image를 만들고 실패했지만 새 코드는 그 할당을 생략한다. 여기에 따른 실패 요청의 no-op Entry 축소는 의도적인 차이이다.
2. 일반 `change(pc,item,mutation)`에서 장착 상태로 거절되는 유효한 항목은 준비 복사를 생성하지 않는다. 잘못된 소유권·오래된 객체는 기존 `entry()` 검사로 계속 거절한다.
3. `changeEnchantLevel(item, expectedLevel, nextLevel)`에서 live/unstaged 대상이 존재하지만 기대 강화 단계·장비 종류·+1 인자가 잘못된 경우는 조기 거절한다. 이미 준비된 변형과 오래된 객체는 기존 검사를 유지한다.

## 실제 메서드 Java 21 비교
- `test_preflight.py`: 191차와 192~194차 실제 메서드를 추출하고 타입이 있는 Java 21 fixture로 실행한다. 이전 상태·새 이미지·실패 예외를 비교한다. 총 77,718개 조건 통과.
- 수량 부족 이전, 장착 아이템 변경, 잘못된 강화 요청에서 불필요한 snapshot/copy 생성 0회를 확인한다.
- 이전 실패로 생성된 191차의 변경 없는 prepared Entry는 비교 대상에서 제외한다(불필요한 준비 행은 의도적으로 생략).

## 변경하지 않은 것
- 거래 원자성, DB preimage, 커밋용 이미지, CacheD receipt/FIFO, 호출자 콜백 및 실패 격리 구조.
- 기존 NPC AI, 네트워크, 방송, CacheD 공통 코드.
- 일반 강화의 전체 파괴 원자성, 카드 수량 복구, 펫 소환 실패 보상은 미완성.

## 한계
Java 21 모의 실행은 실제 MySQL/영속 거래의 ACK loss, 재접속, 서버 재시작을 증명하지 않는다. JFR 할당률 실측과 전체 프로젝트 의존성 타입 컴파일은 수행하지 않았다.

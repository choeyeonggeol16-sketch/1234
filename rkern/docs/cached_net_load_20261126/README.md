# Net DB와 CacheD 혼합 부하

비교 기준은 Net 쿼리와 스키마 수정이 포함된 서버 커밋 `02899b41`이다. 이전에 배포한 Net DB의 테이블 정의를 별도의 스키마에 복제하고 합성 데이터만 넣었다. 측정 대상은 계정 읽기, 인벤토리 복원, 계정·캐릭터 저장과 거래 영수증이다. 지연에는 요청 발행 예정 시각부터 서버 내부 완료까지의 대기가 포함된다.

## 혼합 부하 결과

MariaDB와 JVM을 서로 다른 CPU에 고정하고 Hikari 풀 상한은 8, CacheD 워커는 4로 유지했다. 아래 실행에서는 InnoDB를 커밋마다 로그를 디스크에 쓰도록 설정했다(`innodb_flush_log_at_trx_commit=1`, 바이너리 로그 꺼짐). 800건 예열 후 초당 2,000건의 일정으로 3,200건을 발행했고, 한 소유자의 DB 행을 150ms 동안 잠갔다. 로그인과 인벤토리 조회도 실제 서버와 같은 소유자별 CacheD 접수 경로를 사용했다. 다음 표의 p99는 여섯 종류의 요청 전체를 합친 분포에서 계산했다.

| 비교 | 실처리량 기존 → 수정 (건/초) | 전체 p99 기존 → 수정 |
| --- | ---: | ---: |
| 1차 | 1,330.2 → 1,360.2 | 799.5 → 749.3ms |
| 2차 | 848.8 → 981.8 | 2,159.8 → 1,651.5ms |
| 전체 소스 재빌드 후 역순 비교 | 1,359.6 → 1,418.7 | 743.2 → 656.1ms |

1·2차는 변경된 저장 경로를 기존 빌드 위에 올려 교대로 비교했다. 마지막에는 소스 1,693개를 다시 컴파일해 수정본부터 실행했다. 세 쌍 모두 3,200건을 전부 완료했다. 두 번째 쌍은 요청 발행 스케줄도 많이 밀렸으므로, 이 쌍의 큰 차이를 예상 운영 개선 폭으로 해석하기 어렵다. [실행별 처리량·지연·SQL·락 지표](measurements.tsv)

마지막 비교에서 독립 거래 p99는 746.6→657.1ms, 로그인용 계정 읽기는 747.0→654.0ms, 인벤토리 복원은 737.4→656.1ms였다. 계정 저장 완료 대기는 28.6→72.4ms, 캐릭터 저장 완료 대기는 26.9→73.5ms로 늘었다. 두 저장 지표에는 8개의 시험용 작업자가 `flush` 확인을 시작하기까지의 대기도 포함한다. 같은 실행에서 독립 거래의 CacheD 큐 대기 p99는 수정 후 653.7ms였다. 부하 종료 후 대기 작업·준비 큐 잔류·검출된 DB 및 JVM 데드락은 0건이었고, 예열 포함 영수증 1,964개와 각 소유자의 최종 잔액, 아이템 수량과 성장 이력을 확인했다.

비교를 위해 조회를 별도 읽기 풀에 둔 조건에서도 초당 4,000건씩 5,200건을 발행했다. 수정 전후 실처리량은 1,637.6→1,711.2건/초, 두 번째는 1,740.6→1,721.3건/초로 방향이 엇갈렸다. 인위적인 행 잠금을 해제한 별도 비교에서도 독립 거래 p99가 1초 이상이어서, 잠금 하나를 제거하는 것으로 포화가 해소되지는 않았다. 시험에 사용한 거래 변동은 CacheD를 통해 두 합성 잔액 행에 적용했고, 실제 창고·소지품 SQL과 접속 종료는 별도 회귀 시험으로 검증했다. 클라이언트 왕복 지연과 장시간 운영 서버의 용량은 이번 수치에 포함되지 않는다.

저장 완료 지연을 줄이기 위해 즉시 저장 요청에 한 차례 우선권을 주는 정책도 따로 실험했다. `native-urgent` 행에서 A는 채택한 코드, B는 우선권 실험이다. 계정·캐릭터 저장 p99는 약 49–55ms에서 15–17ms로 줄었다. 반면 실처리량은 1,384→1,347건/초와 1,395→1,278건/초로 모두 감소했고, 독립 거래 p99는 708→770ms와 693→896ms로 늘었다. 로그인과 인벤토리 조회에도 같은 지연 증가가 나타나 기존 순서 정책을 유지했다.

## 변경과 개별 검증

- **거래 커밋**. 자동 커밋으로 대여한 JDBC 연결에서는 수동 트랜잭션을 연 뒤 자동 커밋을 복원하는 호출 하나로 영수증과 아이템 변경을 커밋한다. 원래 수동 모드였던 연결은 명시적 커밋을 유지한다. 커밋 결과나 롤백 성공 여부가 불확실하면 연결을 폐기한 뒤 다른 연결에서 영수증을 확인한다. MariaDB와 Hikari에서 중복 요청, 소유자 불일치, 커밋 직전·직후 응답 유실, 풀 재대여와 JDBC 추적 양쪽 설정을 검사했다. [커밋 회귀 테스트](../../tests/storage/CacheDReceiptClaimRegression.java)
- **저장 큐**. 작업마다 현재 어느 대기 집합에 속하는지 기록한다. 우선순위와 실행 가능 여부가 그대로면 트리에서 삭제하고 다시 넣는 작업을 생략한다. 워커 수, 소유자별 처리 순서, 재시도 시각과 격리 정책을 유지했다. 혼합 대기 작업 1,024개를 사용하는 Java 21 단독 시험에서 상태가 그대로인 작업을 재검사할 때 할당량이 회당 30바이트에서 0바이트로 줄었다. 서로 다른 세 JVM에서 반복했다.
- **캐릭터 저장**. HP·MP 성장 이력을 한 정수 배열에 필요한 만큼 저장하고, 레벨별 증가분이 추가될 때만 저장용 문자열을 다시 만든다. 이전 저장 형식, 과거 데이터의 숫자 표기, 중복과 잘못된 레벨 거절을 검사했다. Java 21 스레드 할당량 측정에서 빈 이력 생성은 1,232→24바이트, 80레벨분의 이력을 반복 직렬화할 때는 2,064→0바이트, 같은 이력을 로그인 때 읽을 때는 약 25,878→1,120바이트였다. 캐릭터별로 현재 저장 문자열 한 개를 유지한다. [레벨별 회귀 테스트](../../tests/storage/CharacterGrowthSnapshotRegression.java)
- **월드 입장**. 스킬·버프·우편·차단 목록의 순서와 네 조회를 유지하면서 DB 연결 대여를 4회에서 1회로 줄였다. 저장된 기억 구슬은 최대 64개씩 묶어 읽는다. 구슬 65개 시험에서 SQL이 65회에서 2회로 줄었고, 구슬별 슬롯 순서·번호를 대조했다. [로그인 회귀 테스트](../../tests/storage/CacheDLoginHydrationRegression.java)

- **여러 아이템 거래**. 같은 준비 구문에 아이템 ID를 다시 바인딩해 잠그기 직전의 값을 확인한다. ID를 오름차순으로 하나씩 잠그는 순서, 검증하는 19개 필드, 첫 불일치에서 중단하는 동작을 유지했다. 두 JDBC 세션이 같은 12개 행을 다루는 개별 시험 4쌍에서 Java 스레드 할당은 거래당 약 173KB에서 66KB로 줄었다. 실행별 p99 중앙값은 4.22→3.45ms였고 한 쌍에서는 증가했다. 소유자나 수량이 다르면 롤백되는지, 아직 검사하지 않은 뒤쪽 행을 다른 세션이 계속 갱신할 수 있는지도 확인했다. [동시성 회귀 테스트](../../tests/storage/CacheDWarehouseInsertConcurrency.java)
- **로그인 공지**. 로그인할 때 안 읽은 첫 공지를 준비 구문 한 번으로 읽는다. 기존에는 공지가 있으면 최대 세 번 조회했다. 공지 번호·한글 본문·줄바꿈·읽을 공지가 없는 계정을 대조했다. 서버가 송신을 접수한 뒤 읽음 표시를 갱신한다.

## CacheD 구조 참고

LU4 리니지 2 참조 코드에서 게임 서버가 CacheD 연결 두 개를 만들고, 캐릭터 상태와 아이템 상태를 서로 다른 주기에 저장하는 경로를 확인했다. 두 연결은 요청별로 선택되므로 이 코드만으로 DB 내부의 캐릭터별 처리 순서나 SQL 워커 수를 판단할 수 없다. RKern에서는 같은 캐릭터의 거래가 저장·적용되는 순서를 유지하고, 서로 다른 캐릭터의 작업을 기존 워커에서 병렬로 처리한다. [LU4 연결 생성](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/L2Server/src/DB.cpp#L1320-L1344) · [캐릭터와 인벤토리 저장 주기](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/L2Server/src/User.cpp#L905-L925)

## 측정 재현

독립된 MariaDB 11.8.9 인스턴스와 Java 21을 사용한다. `CacheDNetMixedLoad 2000 3200`은 초당 2,000건을 발행해 3,200건을 측정한다. 기본 모드에서는 로그인과 인벤토리 읽기도 계정·캐릭터 소유자 순서를 지키는 CacheD 접수 경로를 탄다. `-Drkern.bench.readAdmission=side`는 별도 읽기 풀에서 같은 저장소를 호출하고, `-Drkern.bench.injectRowLock=false`는 인위적인 행 잠금을 생략한다. JDBC 드라이버와 서버 의존성을 클래스패스에 넣고 서버와 같은 Java 설정으로 테스트를 컴파일한다. `RKERN_BENCH_JDBC`, `RKERN_BENCH_USER`, `RKERN_BENCH_REFERENCE_SCHEMA`를 설정하고 비밀번호가 있으면 `RKERN_BENCH_PASSWORD`로 전달한다. 벤치마크 계정은 임시 DB를 만들고 제거하며, 참조 DB에서 테이블 구조를 읽을 권한이 필요하다. 실행 프로그램은 무작위 이름의 자체 스키마만 만들고 삭제한다. [혼합 부하 테스트 소스](../../tests/storage/CacheDNetMixedLoad.java)

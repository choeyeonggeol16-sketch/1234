# CacheD 장애 격리 범위와 LU4 비교

RKern의 기준 커밋은 `b4de2a0c`다. 이후 장애 격리 패치와 비교할 수 있도록 해당 커밋의 운영 코드만 집계했다. LU4는 공개 Open_LU4_L2OFF의 `abbb2e5f474d40cf12539a8e97fddc52474ed95e`에서 로컬로 본문을 확인한 파일을 근거로 삼았다.

## 공개 LU4에서 확인한 경계

- 게임 서버는 `L2Server.cpp`에서 자기 I/O 워커를 시작한 뒤 `CDB::InitCacheD`로 별도 CacheD에 접속하고 버전을 요청한다. `InitCacheD`는 DB 소켓 두 개를 초기화한다. `CDB::RequestLoadUI`와 `RequestSaveUI`는 캐릭터 식별자를 담아 `User::SendDB`로 전달하며, 이 함수는 스레드 로컬 월드 문맥을 설정하고 DB 소켓으로 요청을 보낸다. [서버 시작](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/L2Server/src/L2Server.cpp#L2183-L2200) · [소켓 초기화](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/L2Server/src/DB.cpp#L1320-L1345) · [UI 요청](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/L2Server/src/DB.cpp#L2825-L2837) · [User::SendDB](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/L2Server/src/User.cpp#L3476-L3495)
- `L2_BUILD_CACHED`의 `GetIOThreadCount`는 논리 CPU 수를 최대 16으로 제한한다. CacheD의 `IOThread_common`은 워커에 DB 선택 문맥을 설정하고 타이머와 I/O 완료 콜백을 처리한다. `DBConn`은 DB ID로 풀을 선택하고 소멸 시 연결을 반환한다. 풀에는 마지막 연결 한 개를 남기는 대기 조건이 있다. 이 구조에서 참고할 부분은 게임 I/O, CacheD 요청, DB 연결 대기의 경계다. [I/O 워커 수](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/Shared/src/IOC.cpp#L91-L107) · [CacheD 워커](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/Shared/src/IOC.cpp#L1343-L1433) · [연결 대기](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/Shared/src/DBConn.cpp#L1490-L1536) · [연결 수명](https://github.com/luannbr/Open_LU4_L2OFF/blob/abbb2e5f474d40cf12539a8e97fddc52474ed95e/Shared/src/DBConn.cpp#L1735-L1768)
- 로컬 참조에는 `CacheD/src/Cached.cpp`, `CacheSocket.cpp`, `UserDb.cpp`, `WareHouse.cpp`의 트리 항목만 있어 본문을 분석할 수 없었다. 저장별 락 순서, 커밋 확인과 재시도 정책, 실제 배포의 CacheD 스레드 총수와 장애 복구 동작은 확인 범위 밖이다. [공개 CacheD 소스 트리](https://github.com/luannbr/Open_LU4_L2OFF/tree/abbb2e5f474d40cf12539a8e97fddc52474ed95e/CacheD/src)

## 장애가 공유되는 경계

| 경계 | 기준 동작과 남은 확인 |
| --- | --- |
| JVM·작업 큐 | `CacheD`는 게임 서버 JVM 안에서 4개 워커를 사용한다. 계정·캐릭터·아이템 스냅숏 상한은 각각 16,384·16,384·131,072개, DB 작업 상한은 2,048개다. 포화 직전 4개의 접수 슬롯을 독립 소유자에게 남기며, 일반 `DbJob`은 동시에 최대 3개까지 실행할 수 있다. 소유자와 아이템의 순서 및 준비 큐는 공용 락으로 보호하고 SQL 실행은 락 밖에서 한다. 이 제한으로 특정 소유자의 대기가 완화되지만 공유 DB가 멈추면 나머지 워커도 대기할 수 있다. [큐와 워커](../../src/l1j/server/server/storage/CacheD.java) |
| JDBC·DB 서버 | 직접 JDBC와 CacheD가 하나의 `DatabaseFactory` Hikari 풀과 동일한 설정을 쓴다. 풀에서 연결을 받는 제한은 30초다. `config/Database.ini`의 `MaximumDatabaseConnections`가 풀 크기에 반영되고, URL에서 덮어쓰지 않으면 MySQL·MariaDB 드라이버의 접속과 소켓 응답 제한 기본값은 5초와 30초다. DB 풀 포화, 서버 단절, DB 전체 락은 여러 도메인에 영향을 줄 수 있다. [DatabaseFactory](../../src/l1j/server/DatabaseFactory.java#L57-L114) · [DatabaseConfig](../../src/l1j/server/DatabaseConfig.java) |
| 스키마·커밋 | 시작 시 워커가 InnoDB와 영수증·퀘스트·보상 고유 키를 확인한다. 영수증과 데이터 변경은 한 트랜잭션에 기록한다. 커밋 응답을 잃으면 별도의 같은 풀 연결에서 동일 영수증을 확인하는 경우에만 커밋 처리한다. 확인 실패 시 해당 소유자를 메모리에서 차단한다. 전체 DB 단절 중 확인 연결 확보, 재접속 뒤 정리, 재시작 경계는 따로 검증해야 한다. [트랜잭션](../../src/l1j/server/server/storage/cached/CTransaction.java) · [DB 설치 및 업데이트](../../../database/README.md) |
| 게임 소유자·종료 | DB 커밋 후 남은 게임 소유자의 반영을 완료하도록 종료 시 CacheD를 먼저 비우고 CIO를 내린다. 이후 CacheD와 JDBC 풀을 차례로 닫는다. 기준 코드에서 DB 작업이 비워지지 않으면 종료가 30초 간격으로 대기를 계속하므로 장기 장애 중 종료와 복구를 함께 검증할 필요가 있다. [GameServer 종료](../../src/l1j/server/server/GameServer.java#L619-L650) |
| 기존 시험 범위 | 5,120 TCP 연결, 암호화 프레임, 실제 MariaDB와 합성 계정·캐릭터를 사용했다. 거래 영수증과 최종 잔액을 대조했고 잠금과 포화 뒤 정상화도 관측했다. 장시간 DB 단절, 인증 전체 흐름, 모든 창고·상점 화면, 운영 환경의 장기 메모리 및 지연은 별도 범위다. [5,120명 시험](../cached_5120_20261126/README.md) |

우선 확인할 경로는 DB 응답 지연이나 단절 시 독립 소유자의 진행과 확정되지 않은 커밋의 처리, 직접 JDBC 우회가 게임·스케줄러 스레드를 점유하는 시간, DB 복구나 장기 단절 상태에서의 정상 종료 순서다. 커밋 실패율과 함께 풀 획득 대기, 실행 중인 워커와 작업별 큐 체류, 반영을 기다리는 소유자 수를 나눠 측정해야 같은 지연 현상의 원인을 구별할 수 있다.

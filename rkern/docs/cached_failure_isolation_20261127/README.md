# CacheD 장애 격리와 복구 검증

기준 버전은 5,120명 부하 시험을 마친 `b4de2a0c`다. 이 버전에서 CacheD를 직접 참조하는 운영 코드 142개 파일의 호출 위치 324개를 분류하고, DB 실패가 다른 이용자·게임 스레드·다음 로그인으로 번지는 경로를 조사했다. 호출 수에는 소유자 키 계산도 포함된다. 도메인별 집계와 공개 LU4 리니지 2 소스에서 확인한 게임 서버·CacheD 경계는 [구조 및 조사 범위](coverage.md)에 정리했다.

## 변경과 검증

| 경로 | 기존에 관찰한 문제 | 수정 후 확인한 동작 |
| --- | --- | --- |
| CacheD 작업 접수 | 커밋 결과가 불명확한 소유자와 앞선 공동 작업으로 묶인 계정이 신규 요청을 계속 접수해 공용 큐 2,041칸을 더 차지했다. | 같은 입력에서 추가 접수는 0건이었다. 앞서 접수한 작업의 순서를 지켰고 독립 소유자의 작업은 완료됐다. |
| 계정 로그인과 캐릭터 선택 | 중복 공지·목록 요청이 같은 세션에서 중첩될 수 있었다. 만료 캐릭터 삭제가 계정만 예약하고, 자기 뒤에서 계정과 캐릭터를 기다리는 작업과 서로 기다릴 수 있었다. | 소켓별 로그인 요청 표식을 공지와 목록 단계까지 사용했다. 삭제 시 계정과 캐릭터의 순서를 모두 예약하고 대상 ID와 만료 시각을 다시 확인한다. 선행 세션의 늦은 응답을 무시하는 경우도 검사했다. |
| 인벤토리 자동 저장 | 첫 번째 아이템이 이동·삭제된 경우 같은 주기의 다른 아이템 저장까지 중단될 수 있었다. | 소유자와 세션을 다시 확인하고 독립 아이템 저장을 계속한다. 거래 결과가 아직 게임에 반영되지 않은 아이템은 다음 시도에서 최신 값을 캡처한다. |
| 거래 영수증과 경매 대금 | 일치하는 영수증을 읽은 뒤 JDBC 자원 반환에서 난 오류가 이미 확인한 커밋을 뒤집을 수 있었다. 경매 대금 알림을 위한 추가 DB 조회가 거절되면 확정된 지급 처리까지 실패할 수 있었다. | 영수증을 확인한 시점과 JDBC 정리 실패를 구별했다. 중복 ID의 소유자를 읽지 못하면 새 연결로 확인하고 여전히 불명확하면 해당 거래를 격리한다. 지급 알림이 밀려도 채권은 유지됐고 두 번의 로그인 복구에서 금액 7이 정확히 한 번 지급됐다. |
| 아이템 거래의 시각 비교 | DB가 아이템 시각의 소수 초를 저장 정밀도로 반올림하거나 버리면 자바 시각과 달라져 정상 거래가 거절될 수 있었다. | 불일치가 난 시각에만 현재 DB 연결의 열 정밀도를 적용한다. MariaDB의 절삭·반올림 모드에서 소수 초 0·3·6자리와 자정 경계를 확인했고, 저장 가능한 최소 단위만큼 다른 값은 계속 거절했다. |
| JDBC 시작과 연결 거절 | 실제 연결이 하나도 없는데 초기화가 끝나고, 설정 상한 4개가 20개로 커졌다. | 사용할 수 있는 풀만 공개한다. 실패한 풀은 닫고 게임 초기화를 중단하며 운영 화면에서 다시 시도할 수 있다. 같은 JVM에서 DB를 복구한 후 SELECT에 성공했다. 부분 예열에서는 대여한 연결을 모두 반환하고 설정 상한 4개를 지켰다. 공통 획득 경로에서 연속 256건이 모두 호출자에 실패를 반환했고 스택 로그는 1건이었다. |
| 계정 저장 | 로그인 이름만으로 갱신하고 영향받은 행이 0이어도 완료 처리해, 같은 이름을 다시 등록한 계정에 이전 값이 써질 수 있었다. | 로그인 이름과 계정 ID를 함께 검사한다. 변경값이 같은 경우와 이전 계정이 삭제된 경우를 실DB에서 구별했다. 삭제된 ID의 저장을 기다리던 호출에는 실패를 반환했고, 새 계정의 값은 보존됐다. 새 ID의 저장은 이어서 완료됐다. |
| 일반 아이템 저장 | 소유자가 없는 아이템 갱신이 SQL 큐에 들어가 저장할 수 없는 값으로 재시도를 계속했다. | 일반 저장 및 신규 아이템 등록에서 잘못된 소유자를 접수 전에 거절했다. 기존 소유권, 추가 SQL 0회, 대기 작업 0개와 정상 플러시를 확인했다. |
| 버그베어 경주 | CacheD가 접수를 거절하면 경주 스케줄러가 직접 JDBC를 실행했다. | 경주 시계가 CacheD 접수를 다시 시도하고 워커만 저장한다. 완료되지 않은 경주 기록 한 건과 레이서별 합계만 유지하고, 정상 종료에서 결과를 비운다. 같은 회차의 기록이 충돌하거나 배율 반올림의 중간값으로 동일성을 확증할 수 없으면 경주를 중지하며 독립 작업은 진행한다. |

계정 저장을 직접 호출하는 외부 확장은 네 메서드 `saveLastActive`, `saveLastLogout`, `saveBlessOfAin`, `saveRaidBuff`에서 로그인 이름 다음 인자로 실제 `accountId`를 전달해야 한다. 팩의 호출부와 부하 시험 코드를 함께 변경했다. 이미 소멸한 계정의 저장이 정리된 뒤 이름으로 호출하는 `flushAccount`의 성공은 그 이름의 대기 작업이 비었다는 뜻이다. 삭제된 행에 과거 값이 저장됐다는 확인으로 사용할 수 없다.

## 실제 DB 장애 시험의 범위

같은 호스트의 Java 21 서버와 MariaDB 11.8에서 격리된 Net 스키마와 합성 캐릭터를 사용했다. 실제 암호화 TCP 연결 5,120개를 열고 서버의 로그인·월드·CacheD 등록을 확인했다. 풀의 연결 8개를 모두 대여한 상태에서 계정 저장이 실제 Hikari 획득 시간 초과를 한 번 겪도록 했다. 이 시험의 획득 제한은 1초이며 운영 기본값은 30초다. 별도 구간에서는 풀을 점유한 동안 거래·조회·저장 요청 128건을 겹치고 게임 TCP 에코를 보냈다. 풀을 반환한 뒤 마지막 저장값, 영수증 ID, 양쪽 잔액과 대기열을 검사했다. 비밀번호 인증, 전투와 NPC AI, 물리 장비 장애 및 프로세스 강제 종료는 이 시험 범위에서 제외했다.

| 장애 조건 | 수정본에서 확인한 결과 |
| --- | --- |
| JDBC 연결 8개 전부 점유 | 실제 연결 획득 시간 초과 후에도 계정 변경을 보관했다. 혼합 요청 128건이 모두 완료됐고, 고유 거래 영수증 22개와 양쪽 잔액이 일치했다. 저장 실패 대기 구간과 풀 점유 구간의 에코 최대 왕복 시간은 각각 2.360ms, 10.459ms였다. 기준 버전도 이 복구 시험을 통과했다. |
| MariaDB 프로세스 중단 후 재시작 | 기존 DB 프로세스 종료와 소켓 연결 거절을 확인했다. 같은 게임 JVM에서 준비된 세션 5,120개를 유지했고, DB 중단 중 보낸 에코 16개가 모두 응답했다. 최대 왕복 시간은 1.008ms였다. 계정 저장은 성공을 알리지 않고 대기하다가 DB 복구 후 반영됐다. 이어서 수행한 거래의 영수증 1개, 잔액, 캐릭터 및 아이템 상태를 대조했다. |

두 조건 모두 종료 시 CacheD 대기 작업·게임 세션·대여 중인 다이렉트 버퍼가 0개였으며 검사 시점에 JVM·InnoDB 데드락은 검출되지 않았다. 에코 시간은 단일 실행의 관찰값이다. 세션과 작업별 집계는 [실행 로그 발췌](outage-results.txt)에 있다.

별도 포화 시험에서는 공용 슬롯 2,044개와 독립 작업용 예비 슬롯 4개를 모두 사용한 뒤 다음 접수를 거절했다. 잠금을 푼 후 1,230.9ms 만에 큐를 비웠고, 같은 소유자의 복구 후 갱신까지 총 2,045건이 기대한 순서대로 반영됐다. DB 스키마 변경이나 추가 마이그레이션은 없다. Java 21에서 운영 소스 1,694개를 전체 컴파일했고 기존 경고 6개가 남았다.

### 재현

기존 [5,120명 시험](../cached_5120_20261126/README.md)의 Java 클래스패스와 독립 DB를 사용한다. 풀 고갈 시험은 JVM에 `-Drkern.population.outageOnly=true`를 추가하고 `CacheDCioPopulationLoad 5120 1024`를 실행한다. DB 재시작 시험은 별도의 빈 디렉터리에서 `-Drkern.population.serverOutageOnly=true`를 사용한다. 시험이 `db-stop.ready`를 쓰면 외부 제어기가 그 시험 전용 MariaDB를 정상 종료하고 소켓 연결 거절을 확인한 뒤 `db-stopped`를 만든다. `db-start.ready`가 생기면 같은 데이터 디렉터리·소켓으로 재시작하고 SQL 연결 성공 후 `db-restored`를 만든다. 테스트 코드에는 DB 서비스를 제어하는 명령이나 운영 계정 정보가 들어 있지 않다.

## 운영 경계

DB 전체가 정지하면 신규 DB 의존 작업의 성공 여부를 확정할 수 없다. 현재 구조는 확인된 커밋과 미확인 거래를 구별하고, 불명확한 거래의 소유자에게 추가 변경이 쌓이는 범위를 제한한다. 관리자가 프로세스를 강제로 종료하면 메모리에만 남은 미커밋 변경을 잃을 수 있다. 정상 종료는 저장과 소유자 반영을 기다리므로 DB가 영구적으로 복구되지 않으면 종료 대기도 계속될 수 있다. 직접 JDBC를 사용하는 경로와 CacheD는 물리 DB 및 Hikari 풀을 공유한다.

# RKern Selector와 엔시 구조를 참고한 FFM 네트워크 코어 비교

2026년 11월 27일 측정. **Windows에서 5,000개 연결을 포화시켰을 때 FFM·IOCP는 초당 133,918건, 공유 워커 RKern Selector는 102,819건을 처리했다. 같은 5,000개 연결에 실제 초당 8만 건을 보냈을 때 왕복 p99는 각각 0.190ms와 0.198ms였다.** 포화 처리량은 IOCP가 약 30% 높았다. 동일 부하에서 관측한 p99 차이는 8µs였고 세 번 중 한 번은 Selector가 앞섰다. 이 결과만으로 운영 서버의 지연을 줄이기 위한 전송부 교체를 권하기는 어렵다.

## 무엇을 비교했나

| 이름 | 소켓 I/O와 패킷 실행 방식 |
|---|---|
| RKern 고정 Selector | 기존 Java NIO 전송부의 두 워커가 각자 맡은 연결의 소켓과 패킷을 처리한다. |
| RKern 공유 워커 Selector | 같은 전송부와 두 워커를 쓴다. 소켓 읽기·쓰기는 담당 워커가 맡고, 두 워커가 공용 큐에서 준비된 세션을 가져가 패킷을 처리한다. 세션별 처리 순서를 유지한다. |
| Windows FFM·IOCP | LU4 복원 코드의 공용 완료 큐와 세션별 송신 순서를 참고해 작성한 Java 시제품이다. 실제 Winsock의 비동기 수신·송신을 호출한다. 두 워커가 같은 IOCP에서 완료를 받고, 연결 수락은 별도 스레드가 맡는다. |
| Linux FFM·epoll | 두 워커가 한 epoll 인스턴스를 공유한다. 한 세션의 이벤트를 한 번에 하나씩 처리한다. 초기 단일 워커 에코 실험은 별도 구현을 썼다. |

측정한 FFM 수치는 이 저장소의 Java 구현에 해당한다. 엔시소프트 배포 서버 바이너리의 성능은 측정 범위 밖이다. 시험에 쓴 RKern 전송부 기준 커밋은 `d6edf7a6`이다. ## Windows 공유 워커 맞대결

Windows Server 2025 x64, Temurin JDK 21.0.13에서 두 구현을 같은 러너에 번갈아 띄웠다. 클라이언트는 IPv4 루프백에서 요청을 보내고 응답의 내용, 순서, 체크섬을 확인했다. 공통 핸들러는 258바이트 이동·행동 모의 요청을 처리한다. 실제 게임 로직, 암호화, 방송, DB 및 인터넷 구간은 이번 결과에 포함되지 않는다. [공통 프로토콜](CoreProtocol.java) · [부하 생성기](TransportDriver.java)

### 최대 처리량과 포화 시 지연

연결마다 최대 8건을 연속 전송하고 응답을 받은 뒤 다음 묶음을 보냈다. 매회 3.5초 예열 후 5.5초 측정했고 실행 순서를 바꿨다. 표의 처리량은 초당 검증된 응답 수, p99는 요청 송신부터 클라이언트의 응답 수신까지 걸린 시간이다. 각각 세 번의 중앙값이다.

| 연결 수 | 공유 Selector 처리량 | FFM·IOCP 처리량 | 공유 Selector 왕복 p99 | FFM·IOCP 왕복 p99 |
|---:|---:|---:|---:|---:|
| 1,024 | 113,227건/초 | 147,637건/초 | 108.00ms | 183.50ms |
| 5,000 | 102,819건/초 | 133,918건/초 | 654.31ms | 1,019.22ms |

5,000연결에서는 세 번 모두 IOCP의 처리량이 높았고 공유 Selector의 p99가 낮았다. 각 구현이 서로 다른 처리율로 포화된 상태의 지연이다. 공유 Selector 로그에서는 두 워커 모두 다른 워커 소유 연결의 패킷을 처리했다. 5,000연결 실행 전체에서 그런 패킷의 비율은 회차별 3.2~4.1%였다. [포화 원본 CSV](evidence/windows-shared-selector-vs-iocp.csv) · [워커별 실제 처리 건수](evidence/windows-worker-sharing.csv) · [Windows 실행 기록](https://github.com/choeyeonggeol16-sketch/1234/actions/runs/45948595199)

### 같은 요청량에서의 지연

5,000개 연결을 유지하고 응답과 독립적으로 전송 시각을 예약했다. 예열 2.5초, 측정 5초다. **왕복 p99**는 실제 송신부터, **예약 기준 p99**는 전송 예정 시각부터 응답 수신까지다. 시간 안에 끝난 응답 수로 달성한 처리율을 확인했다.

| 전송 조건 | 구현 | 측정 구간 내 완료율 | 왕복 p99 | 예약 기준 p99 | 유효한 비교 쌍 |
|---|---|---:|---:|---:|---:|
| 초당 8만 건, 8프레임씩 전송 | 공유 Selector | 79,998.4건/초 | 197.7µs | 256.9µs | 3 |
| 초당 8만 건, 8프레임씩 전송 | FFM·IOCP | 79,998.4건/초 | 189.7µs | 225.4µs | 3 |
| 초당 1.6만 건, 단건 전송 | 공유 Selector | 15,999.6건/초 | 245.25µs | 441.25µs | 2 |
| 초당 1.6만 건, 단건 전송 | FFM·IOCP | 15,999.6건/초 | 332.30µs | 573.90µs | 2 |

- **초당 8만 건 묶음 전송.** 양쪽 모두 매회 예약한 400,000건 중 399,992건을 측정 구간 안에 완료했고 나머지 8건까지 검증했다. 측정 요청 손실은 0건이었다. 왕복 p99는 Selector 133.9~220.9µs, IOCP 187.4~195.0µs로 범위가 겹쳤다. [원본 CSV](evidence/windows-80k-batched.csv)
- **초당 1.6만 건 단건 전송.** 완료된 두 쌍에서 양쪽 모두 매회 80,000건 중 79,998건을 시간 안에 완료했다. 세 번째 쌍과 재시도에서는 클라이언트가 연결을 열 때 `BindException: Address already in use`가 발생했다. 한쪽만 성공한 행은 중앙값에서 제외했다. 이 실패로 후속 Actions 실행 전체가 실패로 표시됐으며, 앞선 8만 건 묶음 실험 세 쌍은 정상 완료됐다. [원본 CSV](evidence/windows-16k-single.csv) · [후속 실행 기록](https://github.com/choeyeonggeol16-sketch/1234/actions/runs/45949574517)
- **초당 8만 건 단건 전송의 한계.** 초기 단건 생성기는 5초 구간에 Selector 53,886건/초, IOCP 37,197건/초만 완료했다. 송신 일정 지연 p99가 각각 2.365초와 6.033초였다. 예약한 요청은 나중에 모두 검증했지만 이 두 행은 같은 초당 8만 건을 달성한 결과에서 제외했다. [원본 CSV](evidence/windows-80k-single.csv)

## 고정 워커 Selector와 FFM을 비교한 결과

같은 모의 프로토콜을 사용해 고정 워커 Selector도 별도로 측정했다. Windows 상대는 FFM·IOCP, Linux 상대는 두 워커가 공유하는 FFM·epoll이다. 표는 운영체제와 실행별 3회 중앙값이다.

| 운영체제 | 연결 | 고정 Selector 처리량 | FFM 처리량 | 고정 Selector 왕복 p99 | FFM 왕복 p99 |
|---|---:|---:|---:|---:|---:|
| Windows | 1,024 | 263,921건/초 | 218,699건/초 | 167.77ms | 111.67ms |
| Windows | 5,000 | 246,383건/초 | 201,608건/초 | 662.70ms | 620.76ms |
| Linux | 1,024 | 221,936건/초 | 199,912건/초 | 73.92ms | 88.08ms |
| Linux | 5,000 | 179,768건/초 | 184,321건/초 | 469.76ms | 387.97ms |

Windows 고정 워커 실험과 공유 워커 실험은 **서로 다른 러너 실행**이다. 동일한 IOCP 구현도 5,000연결 중앙값이 실행마다 초당 201,608건과 133,918건으로 달랐다. 고정 Selector의 246,383건과 공유 Selector의 102,819건만으로 공유 큐 도입에 따른 성능 변화를 계산할 수 없다. [Windows 원본 CSV](evidence/windows-fixed-selector-vs-iocp.csv) · [Windows 실행 기록](https://github.com/choeyeonggeol16-sketch/1234/actions/runs/45947135316) · [Linux 원본 CSV](evidence/linux-fixed-selector-vs-ffm.csv)

## Linux에서 분리해 본 두 가지 질문

### 워커 공유가 도움이 되는 부하

RKern Selector와 연결 5,000개, 워커 2개를 유지했다. 같은 연산을 실행하되, 활동량이 많은 유저 32명을 양쪽에 분산하거나 한쪽에 배치했다. 집중 조건에서는 한 워커에 요청 약 95%가 들어왔다. 각 칸은 **포화 처리량(건/초) / 초당 16,000건 예약 시 왕복 p99(ms)** 두 실험의 중앙값이다.

| 활동 유저 배치 | 고정 워커 직접 처리 | 고정 워커별 큐 | 공유 워커 큐 |
|---|---:|---:|---:|
| 양쪽 분산 | 24,586 / 6.14 | 23,848 / 20.20 | 24,203 / 5.45 |
| 한쪽에 집중 | 13,853 / 1,525.47 | 13,517 / 486.20 | 24,496 / 5.14 |

한쪽에 몰리면 공유 워커의 포화 처리량이 직접 처리보다 약 77% 높았다. 분산 조건에서는 직접 처리와 공유 큐 모두 초당 약 2.4만 건이었다. 이는 합성 연산의 배치가 만든 효과다. 54회에 걸쳐 측정 요청 1,242,000건의 응답과 유저별 순서를 확인했다. 초당 11,500건과 16,000건 조건, 큐 대기 p99, 워커별 입력량도 원본에 담았다. [54회 원본 CSV](evidence/linux-worker-placement.csv)

### 단일 워커 TCP 에코에서 FFM이 보인 차이

Linux에서 단일 워커 RKern Selector 에코와 `epoll/recv/send`를 직접 호출하는 단일 워커 FFM 에코를 비교했다. 양쪽 모두 받은 프레임을 그대로 돌려줬다. 이 결과에 엔시식 공유 완료 워커나 공통 게임 모의 핸들러는 들어가지 않았다.

| 연결 | Selector 처리량 | FFM epoll 처리량 | Selector 왕복 p99 | FFM epoll 왕복 p99 |
|---:|---:|---:|---:|---:|
| 1,024 | 81,193건/초 | 118,063건/초 | 144.70ms | 91.23ms |
| 5,000 | 61,010건/초 | 117,934건/초 | 700.45ms | 423.62ms |

초기 대화에서 언급한 **처리량 93% 향상**은 이 5,000연결 에코 결과다. Selector가 한 번 `Connection reset by peer`로 실패해 양쪽을 한 쌍으로 재측정했다. 원인은 특정하지 못했다. 원본의 `used_in_summary` 열이 집계에 사용한 행을 표시한다. 별도 재접속 검증에서는 구현별로 2,000회 연결을 반복한 뒤 열린 소켓 목록이 시작 상태로 돌아왔다. [실패와 재시도를 포함한 원본 CSV](evidence/linux-single-worker-echo.csv) · [재접속 검증 기록](evidence/linux-echo-reconnect.txt)

## 자료를 읽는 기준

각 원본 CSV는 GitHub에서 바로 열 수 있다. 단위는 열 이름에 표시했다. `paired=1`은 같은 회차에서 양쪽 모두 완료해 비교에 채택된 행이다. 포화 실험의 p99와 고정 입력률 실험의 p99는 각각의 부하 조건 안에서 해석해야 한다. 실서비스 도입 판단에는 실제 패킷 구성, 암호화, 브로드캐스트, 게임 로직이 포함된 서버의 처리율과 지연이 추가로 필요하다. [측정 원본 모음](evidence/) · [Windows 실행용 벤치마크](run_bench.py) · [고정 입력률 측정 코드](fixed_load.py)
